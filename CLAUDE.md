# What's an AI Bridge?

ExileApi (PoE1) **and** ExileCore2 (PoE2) plugin that exposes live Path of Exile game state over TCP for AI assistants.

## Quick Start

Run `/setup-mcp` to automatically set up the companion MCP server.

## Layout: one project, two games

```
WhatsAnAiBridge.csproj   single project; compiles Shared\ + the current game's folder
Directory.Build.props    decides $(Game) and TargetFramework (see below)
Shared\                  game-agnostic code: TCP server, DTOs, queries, recording, expression walker
Poe1\                    PoE1 partial class + GlobalUsings (ExileCore, SharpDX, net10)
Poe2\                    PoE2 partial class + GlobalUsings (ExileCore2, System.Drawing, net8)
```

- **Game detection:** the HUD folder is three levels up from the plugin (`<HUD>\Plugins\Source\<Name>`). If it contains `ExileCore2.dll` the build is PoE2; if it contains `ExileCore.dll` it is PoE1. Outside a HUD, pass `-p:Game=poe1|poe2` (default poe1); references then come from `$(exapiPackage)` / `$(exilecore2Package)`.
- **Both HUDs point their `Plugins\Source\Whats An AI Bridge` junction at the repo root.** Build intermediates are split per game (`obj\poe1`, `obj\poe2`).
- **`TargetFramework` lives only in Directory.Build.props.** The PoE2 HUD rewrites any `<TargetFramework>` in a plugin .csproj to `net8.0-windows` when compiling, which would break PoE1.
- **Shared files never import `ExileCore*` directly.** Namespaces come from the per-game `GlobalUsings.cs`.
- **Anything with a different API or different game knowledge goes in the per-game partial** (`Poe1/WhatsAnAiBridge.Poe1.cs`, `Poe2/WhatsAnAiBridge.Poe2.cs`), and the two must declare the same members.
- **No fake values for what a game lacks.** Omit the field (nullable DTO property), call `MarkUnsupported("feature")`, and list it in `UnsupportedFeatures`. Responses carry `game` and `unsupported`, and `hello` reports both.

## In-HUD stats panel (`Shared\StatsPanel.cs`)

- An ImGui window ("Player Stats", id `###bridge_stats_panel`) drawn from `Render()`. It is one surface over the **shared stats view** (`StatsUiState` in the settings: pins, filter, category, selection, sort, `PanelOpen`), the same state the MCP App and agents use.
- **Reads** the state every frame and the 250 ms stats snapshot (`GetStatsSnapshot`); the snapshot skips the HUD's `StatDictionary` (~60-150 us per read) while the raw (id, value) stat vectors are byte-identical to the last read (`SharedStatsRaw.cs`: vectors found once per Stats component by matching the dictionary, a full read and re-validation every 2 s, off with the broken link named in `bridge.self_perf` `statsRawCheck` on any mismatch); **writes only through the mutators** in `Shared\StatsFeature.cs` (`SetStatPinned`, `SetStatsFilter`, `SelectStat`, `SetStatsView`). Never add a second copy of the view state.
- Sync detection: the panel remembers the rev its own writes produced; any other rev change is "remote" (app/agent). A remote selection scrolls the row into view and pulses it; the header pill shows "Synced: <what>" for ~2.5 s.
- `PanelOpen` is the open flag, **closed by default**: the panel was a test surface and must not open on its own. Closing the window calls `SetStatsView(panelOpen: false)`; the settings panel has a "Player stats panel" pill (Stats panel tab, a `.Custom` row) and the control center a setting. Agents and tests never open it unless the user asks (`set_stats_view panelOpen=true` is a visible change on the user's screen). No hotkey.
- Panel-only preferences (section collapse, "Keys" label mode) are `StatsPanel*` ToggleNodes in the settings, not part of the shared view. Window position/size come from the HUD's `imgui.ini`.
- ASCII only in strings (the HUD font has no glyphs beyond it); icons are drawn with the draw list. Card fills derive from the live ImGui style (`SurfaceFill`); life/ES/mana and element hues are fixed. Filter/sort rows are rebuilt only when the snapshot or the view inputs change, and the table draws only the visible rows.

## Agent guide panel (`Shared\GuidePanel.cs`, state in `Shared\AgentGuide.cs`)

- An ImGui window (id `###bridge_guide_panel`) drawn from `Render()` after the stats panel: the agent's current instruction for the user as a sticky card. Agents drive it with `guide.set {title?, instruction?, step?, steps?, status?, detail?, clear?, stepId?, offerDone?, unseenAfterSec?, expiresSec?, ifStep?}` (status adds `unseen`: the user said done and nothing watched changed) and `guide.log {text, kind?: agent|step|result|warn, title?, holdSec?}` (`holdSec` 1-30, default 3: how long the toast stays, `GuideLogEntry.Hold` -> `GuideToast.Life`; a toast held over 3 s is never merged with repeats); `guide.state` reads it back; `guide.user {stepId}` returns the user's answer to a step that offered Done (`{current, mark: null|done|cancelled, markAgoMs, unseen, status}`; a step whose `guide.set` still waits its turn in the attention queue answers `current: false` plus `queued: true, attention, position`). **Who may write the card is the attention queue's call** (below): `guide.set` goes through `GuideSetRequest`, so an instruction from a session without the floor is queued and replayed on its turn (the MCP takes the floor first with `attention.request`, then sets its step), and status / detail / clear on another session's card is `not_your_card`; `ifStep` is never refused and never queued (with an instruction too it goes straight to the card, which takes it only while it shows that step). **A step never outlives its asker:** `ifStep` makes a set (the asker's cleanup `clear`) apply only while the card still shows that step; `expiresSec` clears a waiting step whose agent went quiet (`GuideExpireTick`, from `SessionsTick`, before the sessions lock; the step turn it ran under ends too); a session that disconnected and did not come back within 10 s loses the waiting step it set (`GuideOwnerGone(sessionId)`, by the card's `Session` id, run by the one disconnect cleanup `AttnSessionGoneLocked` as a side effect outside the sessions lock); both post a warn toast. The card records its writer as `Who` (label) and `Session` (id): `GuideSet(p, who, session)`; writes from Render pass their owner explicitly. HUD-run steps (queue runner, flow) carry `who` and no session, so no disconnect clears them. Lock order everywhere: sessions, then guide (never the reverse). State is in memory only.
- **The log is not a panel.** Each new `guide.log` line is a toast under the card for 3 s, the last 0.6 s fading; newest on top, older ones slide down, at most 3 at once. The look is the brand's toast (`DrawGuideToasts`): a slate panel the strip's width with square corners and a hairline border, a 3 px stripe in the kind's tone flush on the left edge, an outlined 18 px glyph in the tone (circle-x error, triangle warn, circle-check result, circle-i agent and step), a caps title (faux bold, fake letter-spacing: one `AddText` per glyph from a cached ASCII table) and the message in caps under it, smaller and muted. `GuideCaps` upper-cases words but keeps identifiers as written (`fire_damage_resistance_%`, `GameController.Player`, `ReAgent`). The title is `guide.log`'s optional `title` (up to 40 chars), else the kind as a word (`STEP 2` while the guide is on a step, `RESULT`, `WARNING`, `ERROR`, `AGENT`); the tones are `ToneNeutral` agent, `ToneAccent` step, `ToneOk` result, `ToneWarn` warn, `ToneBad` error. Colours are fixed (`GuideToastInk` #15171c and friends) so toasts look the same on any HUD theme. Toasts go on the **background draw list** (no window: the mouse passes through) and show even while the card is hidden, anchored under the panel's last position. Toasts carry no hint text. A merged repeat (feed: "x3") shows its count as a chip at the right edge of the title line, tinted in the kind's tone (14% fill, half-strength hairline, the count in the tone at 0.85 f; the title clips short of it), and each repeat bumps the chip over 0.35 s (the tint flares, a ring leaves it) without re-entering the toast or pushing the stack (`Born` keys the slide-in and the push, `At` the life); the "N updates" summary toast after a combat hold swaps the circle-check for a two-stacked-sheets-with-a-check glyph in the same 18 px box. The quiet status dot (attention rule 5) is drawn in the same family at the card's glyph spot: a 6 px disc in the tone on a 1.5 px ink ring, an eased 6 px halo on hover, a 4 s shallow breathe only while the bridge is down, and a toast-styled ink label (foreground draw list, ASCII caps) instead of an ImGui tooltip when there is nothing to bring back. **Verbosity per kind** (`ToastShown`, settings `ToastAgent` off by default, `ToastStep` / `ToastResult` / `ToastWarn` / `ToastError` on): a kind that is off is skipped by the toast stack only (the stack height and the newest-toast push skip it too); the line still goes to the log sheet and `guide.state`. They are plain settings (not permissions): the settings panel (Agent guide tab), the control center (`[Menu]` labels "Toasts: ...", group Agent guide from `[MenuTab]`) and agents through `settings.set` / MCP `hud_settings_set` can change them. The `agent` kind is what the MCP logs for every tool call ("Claude: run_csharp"): off, the user sees only steps, results, warnings and errors while playing. The **log sheet** opens only with the user's own hotkey, `Settings.AgentLogHotkey` (a `HotkeyNodeV2`, **none by default**: then the sheet cannot be opened and only the toasts show; set it in the settings panel's Agent guide tab, "Agent log hotkey", which uses the HUD's own `DrawPickerButton` picker with modifiers and Clear). The key **toggles** the sheet (press to open, press again, or the **Close** pill, to close): a dedicated key is not pressed by accident, so there is no hold delay, and a toggle lets the user select text and press ctrl+c without holding a third key. The sheet is its own window (`###bridge_guide_log`, `NoSavedSettings`, same anchor): the last 20 lines (at most 24 wrapped rows, oldest give way, so it never scrolls), newest at the bottom, in a read-only `InputTextMultiline` so lines can be selected and copied with ctrl+c, plus **Copy all** and **Close** pills. It fades over 0.2 s on close and takes no input while fading; it closes itself when the log is empty or the key is cleared. The key is read through `HotkeyNodeV2.PressedOnce()` (the HUD's `Input`, which polls the key while the game has focus; ImGui only sees keys sent to the overlay window, not the game's; it also honours the core's "ignore hotkeys on focused input"). `GuideLogOpen` is kept in the settings for old saves but unused.
- **The card is the persistent member of the toast family** (`DrawGuideCard`). The look follows syrairc's ExileImGui2 (ExileMaps: its toast stack and `MessageBar`, "the persistent cousin of a toast"), ported by hand, never referenced (no cross-plugin linking): slate ink panel with square corners and a hairline border, the status tone's stripe flush on the left edge, an outlined glyph in the tone, the status as a tracked faux-bold caps title, the body in the text colour and never the tone, and the loud state "tinted rather than filled". Rows: the **title row** (glyph or the flow's "now" badge, `DO THIS NOW` / `TRY AGAIN` / `CHANGE SEEN` / `CAPTURED` / `NOTE`; from the right: dismiss x or Stop, elapsed, the step pill, then the guide's title in dimmed caps in the space left, cached) and the **message row** (the instruction in sentence case - an instruction is read, not shouted). **Loud** (`waiting` / `failed` with an instruction): the message at 1.3 f, a 5 px stripe, a 22 px glyph, the title in the tone; the throb comes from attention (`Urgent`). **Calm**: f, 3 px stripe, 18 px glyph, white title. A third small line carries the status subline (progress dots, captured / failed detail), the agent's `detail`, or the flow plan. **The card grows before it clips** (the user: "sometimes instruction is unclear and it gets cut off"): the message wraps onto up to three lines, loud or calm (`GuideMsgLinesMax`; the captured receipt stays one clipped line), the third line onto two (`GuideSubLinesMax`) when its text is static (detail, the unseen line, captured / failed / unseen sublines; the animated progress and checking lines are short and stay one line). Wraps come from `GuideWrapCache` (`MsgWrap`, `SubWrap`), cached until the text, size, width or line limit changes, with `Clipped` saying whether ".." cut anything: no per-frame allocation. The animated sublines are three cached strings per line indexed by the dot count (`GuideDotted`). Width stays 480 px.
- **Hover, in the toast family** (`GuideHover(title?, body, note?, foot?, tone)`; `GuideTooltip(text)` is its one-line form). Never ImGui's grey tooltip over the card's own lines: an ink panel at most the card's width with a hairline, the tone's stripe on the left, an optional tracked faux-bold caps title and the body wrapped at 0.85 f (body in the text colour, note and foot muted), on the **foreground draw list** at full opacity, placed at the card's x **under the card's whole stack** (`HoverBelowY`: the window, then its toasts or the open log sheet) or above the card when there is no room below, clamped to the screen. Wrapped lines are cached until a text changes (`GuideSame`: same instance, else equal by value, so a per-frame string such as the restart card's tooltip is not re-wrapped). Users: the text block of the card (an InvisibleButton over message and third line, present whenever the card holds more than it shows: something clipped, a title with an instruction, a detail, or an asker worth naming) shows title / full instruction / detail / "Asked by <name>"; the title-row pills (`GuideCardPill`) and the x; `QueuePillButton` (queue, restart and log-sheet pills); the queue strip and the "Will record" line; the ask card (pill hints, Later, the x, again, the question block with "Asked by"); the next strip. The quiet dot keeps its own label (`DrawGuideDotTip`, placed at the dot). `captured` shouts for 4 s then shrinks to a one-line receipt (title dimmed) until the next step. **`done` is not a card:** when the status becomes done, `ObserveGuide` posts a 3 s `result` toast titled DONE with the instruction (the one-line result) and the card hides; `guide.state` still reports `done` for agents. **Reads** `GuideSnapshot()` and `GuideAskSnapshot()` once per frame; the writes are `GuideDismiss()` (the x), `GuideMarkDone()` / `GuideUnmarkDone()` (the Done side) and that done toast. A new instruction, or a return to waiting/failed, flashes the card.
- **The Done side of the card** (`GuideAskView` from `GuideAskSnapshot()`: a step set with `stepId` + `offerDone`, which `await_change` and the queue runner do). The title row's right end is laid out from the edge inwards: the way out first (the x, or the **Stop** pill while a queued step records), then the step's answer. `OfferDone` with no mark: a **Done** pill (`GuideCardPill` Primary: accent fill, a check, ink text - the one thing to press) left of the x / Stop, tooltip "You did it: the agent checks what it watches now instead of waiting"; on `detected` / `settling` it ends the settle wait and captures now. The x on such a card is **Cancel** (tooltip says so; `GuideDismiss` marks the step cancelled and the asker stops; the attention turn behind the card ends as `dismissed`). Every control on the title row (x, Stop, Done, Not done yet) ignores clicks for the click guard (0.5 s) after the card arrived or changed owner (`AskClickGuarded`). **Mark `done` on a waiting card = "checking"** (`GuideChecking`, not a status an agent sets): the card goes calm (look `CHECKING`, accent, spinner glyph, message at f, no throb: `mustAct` in `DrawGuidePanel` is false while checking, so attention's `Urgent` is off), the third line says "Got it - I'm looking for that change..." in the agent's voice, and a **Not done yet** pill (Secondary: hairline, muted) takes the Done back. **`Unseen`** (waiting, no Done, `unseenAfterSec` passed): the card stays as loud as any waiting card (the user may still have to act) and the third line, in near-white (the agent talking, not an error), reads "I can't see that change yet - if you already did it, press Done"; it wins over `detail`. **Status `unseen`** (the step is over: the user said done, the agent saw nothing change): look `COULDN'T SEE IT` in the warn tone, calm (hairline frame, no pulse), an eye-with-a-slash glyph, the subline from `detail` (else "You said done, but nothing I watch changed. I'll look for another way to see it."), dismissible x. Not the user's fault, so never loud. Third-line priority: status subline, checking, unseen line, `detail`, flow plan. Pill tooltips go through `GuideTooltip` (alpha pushed to 1).
- **Attention** (`GuideAttentionFor`, one call per frame in `DrawGuidePanel`, the v1 of `research\display-attention.md`: rules 2, 3 and 7). **Every "how visible is surface X now" decision lives there**; surfaces read their entry of the `GuideAttention` record and never decide for themselves. Inputs travel with the outputs: `Highlights` (boxes on screen, from `HighlightSnapshot()`; the overlay re-resolves after this panel, so they can be a frame old), `Hovered` (io.MousePos against the card's rect last frame: a hit-test, the window takes no focus for it), `HoverAgo`, `NeedsUser` (waiting / failed / progress), `MustAct` (waiting or failed with an instruction: the user must act now; progress states are the agent working), `Overlapped`. Outputs: `CardAlpha`, `CardPulse`, `Urgent`, `CardInput`, `ShowPlan`, `ToastsAllowed`, `CardShift`. Rules now: **act now (rule 8)** - a `MustAct` card is never ghosted, highlight or not: 100% alpha, input on, plan line on, and `Urgent` makes the frame **throb** at 1.25 Hz with a fast attack (the tone's frame flashes to full strength and thickens, two halos swell 3 and 7 px outside it, the card gets a wash of the tone); confined to the card, never full-screen, never faster than ~1.5 Hz. It still never covers a highlight (`GuideAvoid` below). **Ghosting (rule 2)** - otherwise, while highlights are on screen the card targets 15% alpha, no pulse, no plan line, and `NoInputs` (clicks go to the game underneath); hovering it targets 90% and keeps that until 5 s after the mouse leaves; without highlights it is at 100%. The drawer eases the alpha over 0.3 s (`PushStyleVar(Alpha)` before `Begin`; `U()` goes through `GetColorU32`, which applies it; tooltips push 1 back). **Never cover a highlight** - `GuideAvoid` tests the card plus its toast stack at the card's *home* (where the user left it) against every box with an 8 px gap and picks the nearest free offset: right or left of each overlapping box (along the top edge, preferred), else below it, on screen. The window is moved by `SetNextWindowPos(Always)` only while that offset is non-zero (eased 0.3 s, `NoMove` meanwhile so home stays the user's), put back once when clear, and ImGui owns the position again. Toasts and the log sheet anchor under the card, so they move with it. **Combat (rule 1)** - input `Combat` from `CombatNear` (`Shared\GuideToastFeed.cs`: an alive hostile monster within 60 grid of the player, from the HUD's per-type `ValidEntitiesByType[Monster]` list sampled at 4 Hz, distance before `IsHostile`/`IsAlive`, held 3 s after the last one; town, hideout or no player release at once; an exception turns the sense off and names the break in `guide.state` `attention.combatBroken`); output `ToastHold`: `agent` and `result` toasts wait (those already up go down into the hold) and come back when it ends as one toast, "N UPDATES" with the latest line (a single held line comes back as itself). `step`, `warn` and `error` toasts are never held. Output `FloorHidden` (input `RestartUp`): while combat lasts and the card is not hovered, the floor card itself (an instruction or an ask) is not drawn and the dot stands in, in the item's tone; hovering the dot brings it back for 5 s; a restart card keeps the panel up. **Repeats and echoes (rule 6)** - the toast stack is a feed (`FeedGuideToasts`) built from the log as lines arrive: a line equal (kind, title, text) to the newest toast within 10 s bumps its count and restarts it ("RECORDED x3"; lines of kinds that are off don't break a run); while highlights are on screen (`DropEchoes`) a line equal to a visible box label or the highlight title is dropped. The per-kind verbosity applies before anything is held, counted or merged; the log sheet and `guide.state` keep every line. **Quiet dot (rule 5)** - inputs `Quiet` (the 2-minute quiet hide below, or no card at all), `Peekable` (a card or queued step exists), `BridgeDown` (`TcpBridgeServer.IsRunning` false); outputs `CardHidden` (never for a `MustAct` card) and `ShowDot` (only once an agent used the guide this HUD session, or while the bridge is down; not while toasts cover its spot): a 6 px dot where the card was, red while the bridge is down; hovering it (hit-test, no window) brings the card back and rule 7 keeps it 5 s after the mouse leaves; with nothing to bring back it shows a tooltip. `guide.state` carries `attention {combat, heldToasts, quiet, dot, bridgeDown, combatBroken}`. Growing it: add an input to the record and a rule to `GuideAttentionFor`; do not add visibility logic to a drawer.
- **Visibility:** `Settings.ShowAgentGuide` is the switch (Settings tab, "Show Agent Guide"). The panel hides itself when everything is quiet (idle/captured/done/info) and nothing the user could see changed for 2 minutes (a state change, or a toast that showed: lines of kinds that are off, held or dropped do not count, so an agent's tool calls don't keep a quiet card awake), leaving the quiet dot (Attention, rule 5); waiting, failed and progress states stay. It reappears on the next rev change or while the dot is hovered. The log state keeps the last 40 lines.
- **Guided flow on the card** (`Shared\GuideFlow.cs`; `FlowSnapshot()` and `FlowPlan()` read once per frame, nothing written): while a flow is `running` the strip's status glyph becomes the **"now" badge** (filled accent disc with the step number, the same badge as the in-game highlight) and the **live plan** (the best order of actions from where the user is now, re-planned every 100 ms by the engine) collapses to one small line under the instruction: "next: X  +N more", drawn only when attention allows (`ShowPlan`, i.e. not ghosted). The engine's "Not on screen yet" hint arrives in `detail` and takes that line instead when present (the status subline wins over both). When the flow ends `done`, "All N steps done" with a popping check holds the line for 3 s; then the card behaves as before (the engine's done/failed status rules). `ObserveFlow` still tracks plan changes and done-count drops for later use; nothing slides any more.
- **Stays out of the way:** a strip 480 px wide (a title row, the message row, at most one small line; the loud card is taller, never wider), default top-centre at y 10 (the very top of the screen); the user drags it anywhere and `imgui.ini` remembers. Flags `NoFocusOnAppearing | NoBringToFrontOnFocus | NoNav | NoScrollWithMouse`, no title bar, no background (the cards are drawn). It only takes the mouse over its own rectangle, and not at all while ghosted (see Attention). The instruction is one clipped line; a clipped line, or one with a title, shows the whole text in a tooltip on hover.
- **Queue card** (steps from `experiment.queue`, state in `Shared\ExperimentQueue.cs`): drawn under the live card when a step is `queued`, from `QueueSnapshot()` taken once per frame. Calm by design (neutral frame, no pulse, one accent control), and laid out as **two numbered steps so the order cannot be misread**: badge 1 is the **Start recording** button itself (`QueueStart(id, "hud")`: the step takes the attention queue's floor next, ahead of the agents' items, at once when it is free; "first - nothing is recorded before this", **Skip** = `QueueCancel` at the row's right); badge 2 is the instruction, dimmed and prefixed "Then:", with "Only once this card says DO THIS NOW". The first live run failed because a big instruction read as "do this now" - the user acted before Start and the baseline already held the change. Never show a queued instruction prominently. Below: the optional note, "who asked N ago - do it 2x - then 4 more start by themselves" (chained steps, `QueuedStep.Chain`, counted in `QueueViewOf`), and "Will record: memory of PlayerStashTabs[33] (72 bytes)" (click opens the exact watch specs); "+N more" pill when several wait. A queued step keeps the panel visible past the 2-minute quiet hide. While the user has something to do (waiting/failed/progress, or a queued step is recording) the card shrinks to a one-line strip: "QUEUED ..." when it will need Start (never NEXT: that word is the attention queue's), "THEN ... starts by itself" when it is chained to the running step. The running step shows on the live card, whose dismiss x becomes a **Stop** pill (`QueueCancel`) for its duration; the runner sets `offerDone`, so the **Done** pill sits left of Stop with the same checking / unseen feedback (Done captures now, or ends the repeat `unseen` naming the watch specs).
- Same rules as the stats panel: ASCII only (glyphs via the draw list), colours from the live ImGui style (`PanelTheme`, `SurfaceFill`) plus the fixed tones; no ExileCore* imports.
- **Highlights** (`Shared\GuideHighlight.cs` resolves, `Shared\GuideHighlightDraw.cs` draws): `guide.highlight {targets:[{item|path|rect:[x,y,w,h]|text (exact element label, e.g. a stash tab "DUMP", every visible match)|panel+child, label?, tier?: primary|secondary|context, order?, action?: click|rightclick, until?: checked|unchecked|gone}], title?, current?, auto?, durationSec?, clear?}`, `guide.highlight_advance`, `guide.highlight_state`. Targets re-resolve every 100 ms (`Element.GetClientRect()` coords draw 1:1 on the ImGui display, except under the world map's pan container `IngameUi.WorldMap[0]`: there the box is `parent + pan.X * W/2560 + local.X * H/1600`, `(pan.Y + local.Y) * H/1600`, with the pan read raw (no page cache) from WorldMap[0] + an offset calibrated against its Position at rest each time the map opens, and `HighlightSnapshot` moves those boxes with the pan every frame, because the HUD's rects trail a drag. Per-game hint `WorldMapPanOffset` (PoE2 0x100, PoE1 null = off until measured); `guide.highlight_state` reports `worldMapPan` (raw, or cached with the reason). `WorldMapPan` / `CalibratePan` / `OnWorldMap`; finding `ui.worldmap.pan-x-underscaled`). **Sequences auto-advance** (`auto` defaults on): a later step whose target appears becomes current, a met `until` or the current target disappearing ends its step, so `current` moves by itself as the user acts; the overlay keys its animations off `current`/`rev` changes, so quick successive advances read as successive pops. `DrawHighlightsImpl` runs from `Render()` after the guide panel on the **foreground draw list** (over the game UI, no window, no input), only while boxes exist. Interiors stay clear: primary = accent corner brackets, the only thing that pulses (2.6 s, low amplitude); secondary = thin accent frame; context = thin neutral frame. Ordered targets get an 18 px badge on the top-left corner: current = filled accent number, upcoming = neutral ring at under half strength, done = green check; a dotted hint runs from the current step to the next. **Action cue:** a box with `action` gets a 14x20 px mouse glyph outside it (right of the box first), its left or right button filled with the accent; on the current step the button dips and brightens once per 1.4 s with a small click ring (first press 0.7 s after entry, after the ring), upcoming steps show it static at 40%, done steps none. Entry: corners snap in over 0.3 s and the active primary gets one expanding ring (per target, so items snap in when their panel opens; an advance re-snaps only the finished and the new step; a highlight older than 2 s on first draw enters silently). One label pill per target, outside its first box, placed below/above/right/left where it covers no other box, badge, cue or pill (" x3" when an item matched several); the title sits above the active box with "step 2 of 3" or "done".
- **Verdicts (asked targets):** a target with `ask` (a yes/no question about the agent's guess, up to 80 chars) and an optional `key` (correlation id, e.g. `worldmap.stop.10=G2_4_1`) gets a **question strip** instead of its label pill: the step badge's accent disc with "?", the question, and Yes (check, `ToneOk`) / No (cross, `ToneBad`) / Not sure (dim) pills. **Only the pills are an ImGui window** (`##hl_ask_<index>`, no background, no decoration, `NoSavedSettings`, sized to the pills), so those clicks stop at the overlay and everything else stays click-through; the visuals stay on the foreground list. A click calls `HighlightAnswer(index, yes|no|skip)` (`GuideHighlight.cs`): the target's `Answer` is set (the rev does not change: the overlay would re-enter), a `HighlightVerdict` `{seq, id (= key, else hl<rev>.<index>), key, ask, label, answer, at, rect, item|path|text|panel+child, highlightTitle, highlightRev, target}` is kept in memory (last 300) and appended to `<BridgeDirectory>\verdicts\verdicts.jsonl` on a pool thread (the seq continues from the file after a restart), and while observing it is an `agent` event `{method: "user.verdict", params: <verdict>}`. The strip becomes a result pill for 2.2 s (popping glyph, fading out), then the label pill returns and a badge-sized check / cross / dash mark stays on the box's top-right corner (reserved in `Placed`). `guide.verdicts {since?, limit?}` returns `{seq, highlightRev, verdicts, asked (the current highlight's asked targets with answer and onScreen), pending}`; `guide.highlight_state` carries `ask`, `key`, `answer`, `answeredAt` per target and `verdictSeq`. **Highlights are per-session layers** (`_hlLayers`, one `HighlightState` per owner: the session id from `CurrentSession()`, `flow` for a running guided flow, `queue` for a queued step being recorded - those two carry the starting session's label as `Who` - and `anon` for a connection that never said hello). A `guide.highlight` replaces only the caller's layer and `clear: true` clears only it; `clear: true, force: true` clears every layer (the reply lists their names as `clearedLayers`, never `layers`, which is the combined view's objects, and says how many questions went with them). So an asked target survives any other session's call. Revs come from one counter across layers (`_hlRevSeq`), so verdict ids `hl<rev>.<index>` stay unique. `ResolveHighlights` re-resolves every layer's targets every 100 ms and drops a layer whose `durationSec` ran out; sequences, `current`, auto-advance and `guide.highlight_advance` are per layer. The overlay (`DrawHighlightsImpl(List<HighlightLayerView>)`) keeps one `HighlightUiState` per owner (entry animations, answered times) and draws all layers together: frames of every layer, then every badge and verdict mark reserved, then each layer's title and labels, placed against every layer's boxes (`_hlAll`, `_hlPlaced`); with two or more layers the title pill's subline names whose they are. Ask windows are `##hl_ask_<slot>_<index>` (`Slot`: a small number per layer, reused). Reads report the caller's layer at the top level as before plus `layers` (`{layer, session, who, mine, rev, title, current, targets, found, asked, pending, until}`, the combined view): `guide.highlight_state`, and `guide.verdicts`, whose `asked` / `pending` cover the caller's layers (its own plus a flow or queued step it started, matched by label) and `pendingAll` every layer; each verdict carries `layer`, `session`, `who`. Each layer with an unanswered question is a `pilot` blocker for HUD restarts (`Sessions.cs`).
- **Highlights never linger** (bridge rule, whatever an agent asks; the user, 2026-10-10, of an ask chip and a big context rect left over the Water Goddess dialogue: "obnoxious and shouldn't stick around at all"). **Lifetime:** an unanswered ask and a context target get `EndsAt` = set + `HlDefaultLifeSec` (25 s) unless the call gave `durationSec`; the box carries `EndTicks` (that, or the layer's `Until`) and the overlay fades it over the last `HlFadeSec` (1.5 s); then the target is `Expired` (not resolved, drawn or pending; `guide.verdicts` `asked[].expired`; a layer whose targets all expired is dropped). An answer stops an ask's clock (its mark stays); primary / secondary stay until cleared, replaced or `durationSec`. **Step:** a session's highlight set while its own guide step is active (`GuideStepNow()`: `GuideState.StepGen`, bumped when the card's step id or instruction changes, on clear, expiry, disconnect and dismiss) records `StepGen`; `ResolveHighlights` drops it once the generation moves or the status is no longer waiting / detected / settling (captured, done, failed, idle...). The flow and queue layers already clear themselves. **Big panels:** each 100 ms resolve reads the open NPC dialogue, `LargePanels` and `FullscreenPanels` rects (`HlBigPanels`, `_hlPanels`; `guide.highlight_state` `bigPanels`); `HlPanelRule` leaves a box inside one (4 px slack) alone, otherwise context / secondary boxes overlapping one are `Covered` (not drawn, not in `HighlightBoxesOf`, so the guide card ignores them) and unanswered asks are `Docked` (a small pill at the screen edge instead of the strip). Boxes report `covered` / `docked` in `guide.highlight_state`.

## Fail at the broken link (maintenance rule)

Offsets move and HUD APIs change with patches. Code that looks things up must say **which link** broke, at the point it broke. A failure should never surface as "not found" ten calls later.
- Every lookup that can fail records the first failing link by name: the walker segment, the missing member, the panel that isn't open, a child index out of range (with the real child count), the collection item `where` that matched nothing, the value read vs the value wanted. See `Why` in `Shared/GuideHighlight.cs` and `Fail(...)` in `Shared/GuideFlow.cs`.
- Tell **broken** apart from **not now**:
  - A member, type or indexer that no longer exists (walker "No public property or field…", "Could not resolve component type…", "Cannot apply indexer…") is broken: report it at start (preflight) and loudly.
  - A null right now (a panel closed) is normal.
- Diagnostics are part of the result. `guide.flow_state` returns `diagnostics` (why the current step isn't done, why each option isn't available) and `preflight` (paths that no longer resolve).

## Logging: never the HUD's top-left text (`Shared\HudLog.cs`)

The HUD's DebugWindow lines (`LogMessage` / `LogError`) are drawn at the player's top left; the user found them far too busy while playing. **The bridge never calls `LogMessage` / `LogError` / `DebugWindow.*` directly:**
- `LogQuiet(msg)`: routine diagnostics (connections, thread hand-overs, reloads that worked and their warnings). HUD log file only, at Information.
- `LogFault(msg, key?)`: something broke. HUD log file at Error, full text (stacks too); a key is written at most once per 5 s, repeats inside the window (a per-frame exception) are counted and a 1 s timer (stopped in `OnClose` by `HudLogStop`) writes "(N more in the last 5 s)" with the last text when the window closes. Pass a stable key when the text carries ids or ports (the TCP server's faults use `tcp`). Agents find it with MCP `hud_log level=error` (and `hud_plugins` error counts).
- `ToastFault(key, title, toast, msg, kind = "error", holdSec = 8)`: a fault the player must act on: `LogFault` plus one toast per load and key, in the player's words (wording reviewed by Fable). Today: "Agents can't connect" (error, the TCP server didn't start) and "F8 feedback is off" (warn, F8's PluginBridge hooks failed; skipped when the first fired, one restart fixes both).
Both write through the HUD's own Serilog logger (`Core.Logger`, found by reflection: the CI reference set has no Serilog.dll); if that link breaks, messages fall back to the old on-screen lines and the break is named once (a missing member for good; a write that throws is retried after 30 s). Information lines reach the file only while Core.Logger lets Information through (both HUDs' loggers run at Verbose; a HUD build that raises it would drop `LogQuiet` lines silently).

## Bridge protocol (v2)

- Newline-delimited JSON-RPC 2.0 on `127.0.0.1:<port>`. The port and a per-launch random token are written to `<HUD>\<BridgeDirectory>\bridge-port.txt` / `bridge-token.txt` (default `claude-bridge`).
- **Every method requires the token**, including `ping` and `status`. Loopback is reachable by every local account, including the separate `gaming` user.
- `method: "query"` with `params.type` = `hello | player | area | playerstats | ui | stash | entities[:range] | monsters | items | deep:<filter>[:range] | eval:<expr> | describe:<expr> | record:* | recording:* | snapshot`.
- `experiment.queue|queued|result|start|cancel|collected` (`Shared/ExperimentQueue.cs`): guided steps an agent queues for the user to start from the guide card.
  - Nothing is captured before Start. The runner in `Render` then records the baseline, waits for a lasting change and lets it settle, once per repeat. It stores the raw eval / memory.read / memory.collect responses, which the MCP diffs.
  - Saved to `<BridgeDirectory>\experiments\queue.json`. A step that was running when the HUD closed goes back to queued.
- **Plugin pub/sub** (`Shared/PubSub.cs`): other plugins publish events and get replies, with no compile-linking. In-process through PluginBridge (BCL delegate types only): `AIBridge.Publish` `Func<string kind, string json, string>` returns `{ok, seq, subscribers}` (the TCP listeners of that kind seen in the last 20 s: none means nobody handles it now); `AIBridge.Subscribe` `Func<string subscriber, string kindsCsv, Action<string>, string>` delivers each matching event's JSON on the publishing thread (handlers must be cheap and thread-safe; same subscriber replaces, a throwing handler is dropped; plugins re-subscribe when the delegate instance changes, i.e. a bridge reload). TCP: `pubsub.events {since?, kinds?, limit?, subscriber?}` (each event with its `claims`; `subscriber` marks the caller as a listener), `pubsub.claim {seq, stage?=handle, by?}` (exactly once per event and stage, else `claimed` with who and when), `pubsub.release {seq, stage?, reason?}`, `pubsub.publish {kind, data, source?}` (pubsub.* kinds are reserved), `pubsub.status`. Events `{seq, kind, at, t, source, data}` go to a ring of 2000 and `<BridgeDirectory>\pubsub\events.jsonl` (synchronous append: rare events; the sequence and claims continue from the file's last 8 MB after a restart) and, while observing, onto the timeline as kind = the event's kind with `pubSeq` (data clipped over 4 KB). First user: Whats A Route's F8 loop (kinds `feedback`, `route`, `feedback.reply`), dispatched by the MCP's F8 dispatcher. A `route.agent` event published over TCP is stamped with the caller's `Owner` (session id), `OwnerName` and `Hue` before delivery (`WorkStampRouteAgent`).
- **HUD phase: "not now" vs broken** (`Shared/HudState.cs`, DTOs in `Shared/HudStateDtos.cs`, contract in the scaffolding's hud-not-now work, sections 1-3). A 4 Hz worker timer (never the main thread) computes `starting | menu | loading | ready` from `GameController.InGame` / `IsLoading` / `Area.CurrentArea` (every read guarded: a failure keeps the last phase and names the link in the file's `error` and `bridge.self_perf` `hudState`). On a change it writes `<BridgeDirectory>\hud-state.json` atomically (temp + replace; `HudStateDto`: phase, prevPhase, since, seq, heartbeat, tickAt, inGame, loading, lastArea, area, lastLoadMs, pids, listener, startup, recentStartupSec, typicalStartupSec, closeReason, prevCloseReason: the previous HUD's closeReason, set in Initialise and kept for the whole HUD run so restart-hud.ps1's post-start hold can tell a manual restart) and publishes pub/sub `area.loading {from, at}`, `area.ready {area, from, loadMs}` and `hud.phase {phase, prev, since, inGame, area}` (source `bridge`); the file is rewritten every 2 s as a heartbeat. `starting` is written first thing in Initialise; OnClose writes `restarting` (restart-state.json `stopping` in the last 3 min), `user-restart` (an open outage incident for this game on the board in phase `down` or `waitingGame`; announced / holding closes by the other rules) or `closed`; a failed read while `starting` stays `starting`. A bridge reload keeps the HUD's startup and adds no startup sample, and is no close: the HUD calls OnClose for it too, so `HsCloseIsReload` reads the caller's stack (`CloseAllPlugins` = shutdown, `UnloadAssemblyPlugins` / `Reload*` = reload; neither = a close as before) and a reload writes `starting` with `reloading: true` and no closeReason, kept by the next load until its first phase change. The first `ready` after `starting` publishes `hud.phase` only, no `area.ready`, when the area is the one the previous file last saw (adopted quietly); a different area is an arrival (`area.ready`, loadMs null). A reload whose next load never comes (plugin disabled, compile failed) stays `starting` + `reloading`, which the MCP reports as stuckStarting after 150 s. A load past 60 s posts one `warn` toast LONG LOAD "Load screen for N s (from X) - the game, not the HUD. Agents wait." (Fable's wording, 10 s, tag `hudstate:longload`, taken down when the load ends: ExileCore2 ticks and renders the bridge during loads). The file write serializes inside the write lock and clears the dirty mark only up to the version it wrote (`_hsDirtyVer` / `_hsWrittenVer`), so a change racing a write is never lost. **Listener side** (`TcpBridgeServer.Live` = `IBridgeLiveInfo`): `hud.state` (the file object + `tickAgeMs`, `pending`), `outage.set` and `outage.state` are answered on the listener thread; `status` adds `phase`, `phaseSinceMs`, `tickAgeMs`; a queued request still waiting after ~1.5 s while loading or starting is answered `-32010` with data `{reason: hud_loading, phase, since, sinceMs, lastArea, lastLoadMs, retryAfterMs}` (only when it wins the atomic claim `PendingRequest.TryAbandon` against the runner's `TryClaimRun`: a request already running is never answered early, an abandoned one is never run); the 10 s timeout (`-32002`) carries `{reason: hud_timeout, phase, sinceMs, tickAgeMs, lastArea, pending}` and says frozen vs loading vs busy (it abandons a request that never started, and says so when one already running may still complete). **Outage** (`Shared/Outage.cs`, card `Shared/GuidePanelOutage.cs`, every player-visible string in `Shared/OutageCardText.cs`): `outage.set {id, game, phase, reason, by, byLabel?, stopOnly, stopAt?, busy?, ready?, clear?}` shows the planned-restart card at the top of the stack (keeps the panel up, drawn in combat like the restart card, calm in every form): announced / holding = waits for the busy agents (warn, bullets with time left / busy for) or, nobody busy, asks for the press (the runner never stops on "nothing busy" alone); after Restart now "Stopping the HUD"; phase down with `stopAt` ahead = the stopping countdown (the three steps, HUD startup from `typicalStartupSec`, Cancel). `stopAt` is kept while the phase stays and cleared by a phase change without it. Restart now / Not now / Cancel publish `outage.answer {id, answer: now|notNow, at}` from a pool thread (Cancel = notNow, accepted after now only while the countdown runs); `outage.state` -> `{id, phase, stopAt, answer, answeredAt, busy, ready, partiesFrom, lease}`. The bridge is the only author of outage toasts: RESTART CANCELLED, RESTART NOW (over busy agents), HUD STOPS - YOUR TURN (down without a countdown), and after the restart HUD IS UP (menu / loading, tagged `outage:waitingGame`, retired on the first in-game tick through `GuideLogEntry.Tag` + `GuideToastRetire`) and BACK (elapsed from the board's down `phaseAt`) (busy / ready from present sessions' blockers, leases and attention items unless the MCP passed its own). At load, an open outage for this game in `down | waitingGame` on `%LOCALAPPDATA%\Hexile\incidents.json` (`HEXILE_INCIDENT_DIR` in tests) becomes the lease `L-outage-<id>` ("user restart <id>", kind other), renewed until the phase is `ready`.
- **Work items** (`Shared/Work.cs`, contract `research/f8-agent-ux.md` sections 3, 5, 8, 11 in the scaffolding): one item per F8 press (`f8:<seq>`, kind `F8`) and per session task (key = session id, kind `Task`), `AgentWorkDto` (PascalCase, nulls omitted). **F8 items are built from pub/sub, not from calls:** `PubPublish` hands `feedback`, `feedback.reply`, `route.agent`, `route.agent.progress` and `route` events to a lock-free inbox (`WorkEnqueue`), applied under the sessions lock by `SessionsTick` (`WorkTickLocked`) or first thing in a `work.*` call: `feedback` creates the item at `Pressed` (a `works`-only press is recorded `Done` "Noted: works here" with a 1.2 s `NOTED` toast, C7); `feedback.reply` moves `Stage` / `WaitingOn` / `Text` / `Detail` / `Ask` / `Pr` (keys in either casing; legacy `status` queued/claimed/working/done/failed maps to Queued/Claimed/Investigating/Done/Failed; a late non-final reply never reopens a final item); the Route plugin's `route` trace `route-reloaded` / `live-reloaded` moves items in Investigating / Fixing to `LiveFix`; `route.agent` / `route.agent.progress` keep each owner's agent route (`_agentRoutes`). The owner of an F8 item is the session labelled `route-f8-<seq>` once it says hello. **`WaitingOn = Player` is derived** (never accepted): the owner's open attention item (ask / step / flow, queued or showing), its guide step waiting / detected / settling, an unanswered asked highlight in its layer (`HighlightAskTextByLayer`), a queued experiment step of its own, or its agent route on a `Manual` step; `Ask` (only while Player; the agent's own `Ask` line is kept as `AskSet`, the fallback text) and `NeedsYou` (answer | step | recording | route) say which. An F8 item's owner is re-linked to a new connected `route-f8-<seq>` session while the linked one is not connected; a press applied after its reply fills the bare item in; a late reply for a press that ended and left `recent` is ignored (this load). Also derived at 4 Hz: `OwnerName`, `Hue` (-1 without owner), `Stale`, `NobodyListening` (still Pressed 30 s after the press), `Stalled` (a CI / review / restart / agent wait over 90 s, or an F8 stage unchanged 15 min), `Route`. TCP: `work.set {Key?, Kind?, Title?, Stage?, Text?, Detail?, Pr?, Ref?, WaitingOn?}` (the caller's own item; `f8:<seq>` / `Ref` only from infra or that press's handler; `WaitingOn` Player refused as `waiting_on_player`) -> `{ok, item}`; `work.list {activeOnly?}` -> `{ok, rev, items, recent}`; `work.end {Key?, Stage?: Done|Failed|Dropped, Text?}` -> `{ok, item}`; `session.list` adds `work[]` per session and top-level `work[]` / `recent[]`. Every change publishes kind `work` (the item) at most once a second per item, after the lock. Final items stay 10 min (`recent`); a task whose session is gone 30 min and an F8 item with no news for 3 h (`Dropped`) leave. "work" events are published by one pool worker (never on the render thread). Active items persist (serialized writes, newest snapshot wins) in `<BridgeDirectory>\work\items.json` (each entry checked on load; a bad file is logged and ignored). **Toasts** on F8 stage changes through `GuideLog` (names via `AgentsView.NameOf`): `QUEUED`, `ON IT` (result), `TRY IT NOW` (step), `DONE #n` (result, 20 s), `FAILED #n` (error, 30 s), `DROPPED #n` (agent), and one `STILL SHIPPING` (agent) per wait over 90 s. **An agent route that leads the player** is a `route` blocker (`WorkRouteBlockersLocked`, not pilot): its owner's Doing ("leading you to <step label>") and a restart waits for it, only while the owner is connected and within the route's ttl. **For the drawer:** `WorkSnapshot()` -> `WorkView {Rev, Rows (board order: needs you, F8 by seq, tasks, stale), F8Rows, Recent, Active, NeedsYouCount, AnyF8Running, RecentFailedAt}` of immutable `WorkRowView`s (label, request, phase index and reached phase, stage word, `WorkTone`, needs-you text, `WorkTailKind` + tail, timestamps, hover title / body / note / foot), rebuilt by the tick only when `_workRev` moved, read per frame by reference; the chip hover lists the rows until the board replaces it. **PluginBridge:** `AIBridge.WorkList` `Func<string>` (JSON array: active plus recent), `AIBridge.HighlightFor` `Func<string ownerSession, string json, string>` (a `guide.highlight` params object drawn in that session's layer as if it had called it - asks queue behind its turn, lifetime and panel rules apply, `durationSec` defaults to 25 s; `{"clear":true}` clears that layer only; errors `missing_owner`, `bad_json`, `unknown_session`, `owner_gone`); both answer `bridge_reloaded` after the bridge reloads (`WorkClose`).
- `data.find_value` / `data.find_result`: a background scan of all loaded tables for ids seen in memory.
- `observe.start|stop|status|events` (`Shared/Observer.cs`): passive observation while the user plays. The runner in `Render` runs while on and in game (panels 10 Hz, area and level 2 Hz, entities 0.5 Hz, layers at their own rates, the hud lane every frame):
  - **Layers** (`Shared/ObserveLayers.cs`) are runtime specs, not code: `{id, path, mode, hz, enabled?, key?, props?}`, any walker path in one of five generic modes, through reflection:
    - `struct`: the object's cached offsets struct read raw (leaf backend) and diffed, each changed range named by the runtime layout (HUD property, else struct field; null = unmapped). For server-sent state.
    - `props`: its public scalar properties. `dict`: an `IDictionary` (keys added, removed, values changed). `list`: a collection's items added and removed, by identity (`key`, default `Address`). `each`: a collection with a few values per item, `props` = 1-8 dotted sub-paths of the item, keyed by `key` (a dotted sub-path too); unit `<key>.<prop>`. A sub-path segment that doesn't exist is a broken link (preflighted on the first item).
    - Defaults: `server` (`ServerData`, struct, 10 Hz: 34 KB on PoE2), `stats` (the player's `StatDictionary`, dict, 4 Hz), `life` (`Life`, props, 4 Hz), `buffs` (`BuffsList`, list by `Name`, 4 Hz) and `inventories` (`ServerData.PlayerInventories`, each, 2 Hz: `Inventory.Hash` and `Inventory.ItemCount` per `TypeId`, unique on PoE2's 118). Defaults apply only to a fresh state; existing specs are kept. `observe.layers`, `observe.layer_set` (preflight: a path or mode that doesn't fit is refused, naming the link), `observe.layer_remove`. Specs persist in `observestate.json`.
    - The mode check runs once per resolved type: for `struct` it boxes the whole cached struct (34 KB for ServerData), which every tick made the observer allocate ~1.6 MB/s.
    - Events: `layer` `{layer, mode, unit, name, old, new, ...}` (struct adds `off`, `len`, `i64` of the aligned 8 bytes whenever the change fits them and `i32` of the aligned 4 when it fits those, so every change of a unit has one comparable width; dict/props add `delta`, `change`). A unit (struct: its 256-byte block) changing over 20 times in 10 s becomes one `layer.noisy` and is then only counted. `observe.layer_map {layer, unmappedOnly?, minChanges?, sort?, limit?}` lists every unit that changed (`observe.server_map` = layer server): the mapping worklist.
    - Values are compared as objects and formatted only when they change; a 4 ms per tick budget spreads layers over frames. A layer whose path breaks stops with `broken` (status) instead of retrying.
    - **Per-tick fast paths** (measured with `bridge.self_perf` `observerParts` and `layers`: per layer avg/max us, the path resolve's share, bytes per tick; also `perf` in each layer's status): walker paths are parsed once and `GetComponent<T>` becomes a compiled call (`MemberIndex.Call`); `struct` reads raw at the known address and resolves the path again once a second; `dict` over a generic dictionary diffs in its own types (no boxing), and over `Stats.StatDictionary` it reads the dictionary only when the raw (id, value) pairs changed (a per-layer `StatsRawGate`, `rawGate` in status, same validation and broken-link rule as the snapshot's); `list` keys items by the key's value and reads an item's preview once, when it appears; `each` keeps per item where its shared pointers led (followed again at every 5 s listing) and reuses the last values while the bytes match, confirming any differing byte through the whole chain. New per-tick work: measure it there first, and keep a quiet tick allocation-free.
  - **Every event** carries `t` (ms on one process-wide clock) and `frame` (ImGui frame count), so layers line up; the journal is written once per tick, not per event.
  - Top-level UI panels opening or closing, with the IngameUIElements property that maps each one, or none, at 10 Hz once the visibility bit is calibrated (2 Hz on the `IsVisibleLocal` fallback); the panel list itself is refreshed once a second. An unmapped panel is saved with its first texts and 512 bytes at its address.
  - **UI catalogue** (`Shared/UiCatalogue.cs`, `observe.ui_catalogue {query?, key?, options?}`): a panel that opens is walked 300 ms later, 1.2 s later and 350 ms after each left-button release inside its rect (+40 px; `Input.IsKeyDown(VK_LBUTTON)` and ImGui's mouse position, read only), breadth-first over visible children like `FindByText` (at most 600 elements, depth 14, 80 texts), one walk at a time sliced to 500 us per frame (`UcSliceUs`; children checked 8 per budget test, elements with over 300 children not opened; the first observer tick of a HUD load runs a 3 ms warm-up walk on the render thread so the JIT never lands on a capture while playing - never walk the UI off the render thread), and merged into one entry per fingerprint (`NpcDialog|<NpcName>`, else `<mapped or panel>|<first PanelTexts text>`) with each text's child path, rect, `clickable` (a hint: `ElementFlags.DetectsHover` on it or its parent, never the panel root; PoE2 only; dialogue buttons often lack it) and a `highlight` recipe (text + within when unique in its view, else panel + child). Persisted to `observe\ui-catalogue.json` (atomic, at the 500 ms flush, only when changed; 400 entries, 120 options each). A capture costs ~13 us and ~5 KB per element visited; `cost` in the reply has the last and worst.
  - **hud** lane (`Shared/ObserveHud.cs`): a frame at least 50 ms and 2.5x the moving average becomes `{cause: spike, intervalMs, typicalMs, gcMs, gen0..2}` (one per 2 s, the rest counted in `suppressed`; gaps over 1.5 s are the overlay hidden or a load, skipped); plugin reloads `{cause: reload, plugin, ok, durationMs}`. So HUD hiccups aren't read as game events.
  - **agent** lane: every bridge call that changes what the user sees or what the HUD does (`AgentMethods`: guide, highlight, flow, experiment, reload, settings, focus, script, measurements, stats view, layer specs) as `{method, params}`, long strings clipped, secret settings values redacted.
  - Area and level changes, and new entity metadata prefixes (every 2 s).
  - Events go to a ring of 1000 and to `<BridgeDirectory>\observe\journal.jsonl`, rotated to `journal.1.jsonl` at 128 MB (one generation kept; at start the sequence continues from both). The on/off state survives restarts (`observe\state.json`).
- Structured methods with named params: `stats.*` (shared stats view), `recording.*` (stateless playback), and `hud.*` (dev loop):
  - `hud.plugins` lists loaded and failed source plugins.
  - `hud.bridge_methods` lists everything registered on `GameController.PluginBridge` with signatures; `hud.bridge_call {name, args?}` invokes one of them (scalar arguments only: numbers, strings, bools, enums) and returns `{ok, name, signature, resultType: json|text|value|null, result, ms}`, a string result that parses as JSON already parsed (`Shared/HudIntrospection.cs`). Errors name the link: `method_missing` (with what is registered: the plugin is not loaded, or an older build), `not_a_delegate`, `arity_mismatch`, `unsupported_parameter`, `bad_argument`, `invoke_failed` (the exception). It runs whatever the plugin method does; MCP `route_state` reads `WhatsARoute.GetState` through it.
  - `hud.reload_plugin {name}` queues a recompile of one source plugin, like the menu's Reload button. `Render` hands it to the HUD's `NextFrameTask` hook, so it runs on the main thread at the start of the next `Core.Tick`, outside the HUD's `foreach` over `pluginManager.Plugins` (reloading from inside `Render` changed that list mid-loop: "Collection was modified" in `Core.Tick`). The HUD pauses while compiling. The bridge refuses to reload itself. The setting is `AllowPluginReload`.
  - `hud.reload_status` reports the queued reload and the last result. The watchdog answers it even while the HUD is compiling.
  - `PluginManager.ReloadSourcePlugin` is internal on both HUDs and is called by reflection. Check it with the MCP's `hud_type` after HUD updates.

Replies to agents name sessions by label; everything the player sees names them by display name. **Arbiter** (`AttnArbitrateLocked`, on every change and from `SessionsTick` at 4 Hz, under the sessions lock; side effects such as replays and card clears run after it): no new turn while a restart waits or is granted, in combat (`CombatNear`), on a loading screen or in the Esc menu; then what the player Started (queued experiment steps) first, then round-robin by session (the session waiting longest since its last turn, its oldest item); calm items only when calm (town or hideout; or no hostile 8 s and no mouse/key input 5 s via `GetLastInputInfo` or a large panel open). **Ownership:** `guide.set` with an instruction, `guide.flow` and `experiment.start` from a session without the floor become implicit queued items that replay the call on their turn (reply `{queued: true, attention, position, ahead, message}`); the MCP's `await_change` takes the floor first (`attention.request`), so its `guide.set` shows at once and `guide.user` reads its own step. Status / detail / clear on another session's card is `not_your_card` (`ifStep` never is, nor queued); flow stop and `experiment.cancel` act on the caller's own only (`not_yours`). A free floor is taken implicitly (a plain `guide.set` turn ends when its card rests). Granting the floor to a new owner clears the previous owner's card (`GuideClearUnlessOwnedBy`, by session id, by label for HUD-run cards). Asked highlights from a non-holder draw their boxes but hold their question strips (`HighlightState.AsksHeld`, not a restart blocker while held) behind one ask item; its turn releases them with a full 25 s lifetime (the clock ran while held, so the boxes never linger), and the item ends `answered`, `expired` (`asks_expired`), or `cancelled` (`no_questions`, `highlight_gone`). **Later** re-queues the ask as calm, not before 180 s then 600 s; the third is `dismissed` (`later_x3`). A showing ask expires after `showTtlSec` (900) from `visibleSince` (`unanswered`); identical asks of different sessions within 60 s share one card and one answer (one arriving while the card is up joins it; when the leader is withdrawn the first follower keeps the card). **Cleanup, one path** (`AttnSessionGoneLocked`): a session disconnected for 10 s without coming back has its open items cancelled, its waiting step cleared from the card (`GuideOwnerGone`) and its highlight layer dropped; a reconnect within the grace keeps all of it. HUD-run work outlives its asker: a queued experiment step (`Detached`; also one its agent started with `experiment.start` once it records) and a running flow (its turn ends with the flow). An `expiresSec` card that times out ends the step turn under it too. **No turn holds the player for nothing** while someone else waits (an item in line or a restart, for which the holder is a blocker): an explicit step / flow turn (`attention.request`) with no card or flow of its own up for 30 s ends `turn_idle`, a step turn whose connected agent sent nothing for 5 min ends `owner_quiet` (its waiting card goes, "<name> went quiet"); an `attention.request` from a session holding an implicit turn takes it over (`superseded`). Restored asks whose session does not say hello again within 60 s of the load are cancelled (`owner_gone`); each restored entry is checked first (`AttnRestoredOk`: bad ones skipped and counted in the log, orphaned followers stand alone), and the tick is guarded, so a broken `queue.json` never breaks the HUD. Queued asks persist in `<BridgeDirectory>\attention\queue.json`. Hues: `session.hello` assigns `hue` 0-5 (FNV hash of the label, moved off hues other connected sessions hold, kept by the session across re-hellos).
  - **On screen** (`attention-queue-ui.md`; `Shared/GuidePanelAsk.cs` the floor's slot and the ask card, `Shared/GuidePanelQueue.cs` the next strip and the dot's look, `GuidePanelSessions.cs` the restart card; `GuidePanel.cs` only has the call-site hooks), built on the card above (toast family, `GuideWrapCache`, `GuideHover`): the **ask card** is the live card with the status `QUESTION` (the `?` badge of asked highlights, the question faux bold on up to two wrapped lines, 2-4 choice pills of equal weight with `Later` pinned at the right end of the first row, the x on the title row = `dismissed`, an optional detail footer on up to two lines; hovers - a pill's hint, Later, the x, again, and the question block whenever something is clipped or the asker is worth naming - are `GuideHover` panels; `urgency=now` = stripe 5 and the calm frame pulse, never the Urgent throb; it softens to the calm look after 60 s ignored; a re-ask within 60 s of the player's x arrives without flash or pulse; back from Later it carries an `again` pill). **Names and who-dots** (6 px disc in the session's hue, `AttnHuePalette`, violet rose sky orange sand slate) precede the agent's display name (`AgentsView.NameOf` by session id) on the ask and instruction cards' title rows, the next strip and the restart card; the cards name their owner only when it is not the obvious single agent (`GuideShowWho`: two or more agents active, or another one in line). **Hand-over** (`AskSlotUp`): a click shows the receipt (chosen pill fills, others 35%, elapsed reads `answered`, 0.8 s), the card fades 0.25 s, the slot stays empty for the gap 0.6 s at the old height (waiting up to 2 s for the mouse to leave the pill row), then the next card arrives washed in its owner's **hue** when the owner changed and with its controls inert for the click guard 0.5 s (the instruction card's x, Stop, Done and Not done yet too). The panel tells the bridge when the slot is free (`AttnSlotBusyUntil`): the next card's `visibleSince`, a queued call's replay (`ReplayDue`, run from the tick) and a restart's countdown start (`AttnSlotTopAtLocked`, `RestartEvaluateLocked`) all wait for that moment plus the gap. **Combat** hides the floor card (ask or instruction, `GuideAttention.FloorHidden`) and the dot in the item's tone stands in; hovering brings it back for 5 s; a restart card keeps the panel up. **The next strip** is the one line that names agents (it replaced both the sessions strip and the "who is asking" strip; the sessions chip beside the card counts who shares the HUD and never names who is next), drawn only while the panel is up anyway and only when it is not the obvious single agent (`NextStripWanted`): with someone in line `NEXT` (`THEN` while a restart card is on screen) + who-dot + `Name: question or title` + one tail (`+N more` / `when things calm down` / `after this`), frozen through a hand-over, hover lists the queue (6 rows, then `+N more`); with nobody in line but two or more agents asking at once, `WHO IS ASKING` + who-dots and names, hover "Name: what it asks" (`AskWords`). Never idle or disconnected sessions, branches or folders (the user: "I have no idea what 'system32 layer-test - main - main' mean"). **Dot**: accent and steady while items wait (or a granted ask is not visible yet), hover label `N WAITING - NAME, NAME`; hovering it then gives the floor to the next item regardless of calm (`AttnUserPeek`). **Toasts** (display names): `QUEUED` (agent kind) when an ask lines up behind a holder, `result` `<NAME>` / `<label>` on an answer, `Later` (agent kind), `UNANSWERED`, `WITHDRAWN`, `Queued step` with its place in line.
- **HUD-update drift preflight** (`Shared/HudLinks.cs` table, `Shared/Preflight.cs`): every private/internal reflection target the bridge reaches (Memory._backend and the paged backend's inner field, TryReadMemory, PluginManager.ReloadSourcePlugin, PluginBridge._methods, Core.Logger + Information/Error, ImGuiRenderer.Update/Render, Overlay.ReplaceFontIfRequired, MonoMod's ReflectionHelper caches, Harmony's detours/state/originals/locker, ArrayPool<byte>.Shared internals) is one `HudLink`, and **the call sites resolve through it** (`link.FieldOn(type)`, `.Method`, `.Broken(type)` for the error text), so the preflight checks exactly what the code uses. **A new private/internal reflection target goes into that table, never a bare `GetField("_x", NonPublic)`.** Checked in Initialise (and again once 0Harmony loads: Harmony links are `not_now` until then; **never touch a Harmony type before `HarmonyLoadError`**, it would load 0Harmony into the plugin context and every patch fails); the stamp (HUD version + module id, .NET) is compared with `<BridgeDirectory>\reflection-preflight.json` from the previous check (`changedFrom` = an update). Rows: `ok | broken` (type, member, expected shape, what is there instead: same name of another kind, near names, fields of the wanted type) `| not_now | blocked` (needs a broken link). hello carries the summary as `reflection` (MCP bridge_status, hud_health_report adds a finding per broken link); a check that itself threw is `failed: true` + `error` (its zero counts are "unknown", never "0 broken"), `reflection.preflight {refresh?, simulateBroken?: <link id>, simulateFailed?}` the rows; a break is a `LogFault` at load. Route's `FreshView.cs` has its own copy of the Memory._backend hack, not covered here.
- **DTO contract** (`Shared/ContractSchema.cs`): every class with a `[JsonProperty]` member, and every class or enum those reach, reflected once per load through Newtonsoft's own `DefaultContractResolver` (so names, `[JsonIgnore]` and `[JsonExtensionData]` (`open`) are exactly what `Serialize` writes) into `{name, kind: object|enum, open?, fields: [{json, clr, type, clrType, nullable, omitNull?}], values?}`. Shapes: `string | integer | number | bool | datetime | any | object:<T> | enum:<T> | list<...> | map<...> | external:<clr>` (enums go out as integers). hello carries `contract {version, hash, typeCount, error?}` (hash = first 16 hex of SHA-256 over the wire-relevant parts only); `contract.schema {type?}` returns the whole schema, or one type and everything it reaches. The MCP keeps a committed snapshot and checks its mirrored DTOs against it (offline test) and against the live schema when the hash moves (bridge_status / hud_health_report "contract drift"). **A new DTO needs nothing extra; a renamed or retyped JSON field is drift the MCP will name: refresh its snapshot (`dotnet run --project Tests -- --refresh-contract`) and fix the mirror in the same change.**
- `bridge.self_perf` (`Shared/SelfPerf.cs`): the bridge's own time and allocation per Render step, averaged since the previous call (always on, allocation-free). Check our own cost with this after changing per-frame code, then `profile.plugin name="Whats An AI Bridge" method=<step>` for the method.
- `RawRead<T>` (`Shared/RawMemory.cs`): allocation-free small reads straight from the leaf memory backend. Use it for scattered per-tick reads: `Memory.Read` on an uncached page rents a 4 KB page that mostly ends up as garbage.
- `object.explore {path, offset, limit, csharp?}` (`Shared/ObjectExplorer.cs`) returns one level of the object model at a walker path, for mapping data out:
  - **For the node and each child:** type, kind, a one-line preview (structs as `X=1 Y=2`, objects with their Name/RenderName and visibility), counts, the walker `path`, and null-safe `csharp`. Dictionaries with enum keys get typed keys (`Stats?[GameStat.MaximumLife]`).
  - **Entities** also list their components, as `GetComponent<T>()` paths.
  - **Paging:** collections are paged with `offset`/`limit`.
  - **Time budget:** reads run on the main thread under a 60 ms budget, and unread members are listed in `skipped`. Getters taking 5 ms or more get `slowMs`.
  - **Shared resolver:** `ExpressionWalker.Resolve` is the one path resolver behind `eval:`, `describe:` and explore.
- `object.find {path, name?, value?, depth?=4, maxNodes?=5000, timeMs?=200, maxMatches?=100, listLimit?=200, components?=true}` and `object.snapshot {path, depth?=3, maxNodes?=2000, maxLeaves?=5000, timeMs?=100, listLimit?=50, components?=false}` (`Shared/ObjectSearch.cs`, DTOs `ObjectFindResponse` / `ObjectSnapshotResponse` in `BridgeDtos.cs`): the graph walk in one request (MCP `find_in_object`, `watch_object` past depth 2). Breadth-first over `MemberIndex.Readable` members, list items, dictionary entries and entity components (explore's rules: walker path + null-safe C# per child, no paths under an indexed path), skipping blocked types, plumbing and `Owner`, never opening an object twice (reference, or same type at the same `Address`). `budget` says what it read and skipped (`nodesOpened`, `membersRead`, `cycles`, `plumbing`, `blocked`, `atDepthLimit`, `itemsSkipped`, `getterErrors`, `elapsedMs`), `truncated {reason: nodes|time|matches|leaves, at, pending, hint}` where it stopped, `errors` the first 20 getters that threw, `aliases` the first 30 objects reached again by a second path (not opened twice: a match inside is listed under `sameAs`); a root that doesn't resolve is `{error: resolve_failed, message (the walker's broken segment), path}`. Snapshot leaves are keyed by walker sub-path (`Health.Current`, `Buffs[0].Name`, `Buffs.Count`, `Stats["MaximumLife"]`). Main thread: `timeMs` bounds the frame it costs.
- **Reflection core** (`Shared/MemberIndex.cs`): the one place that looks members and types up by name. Never call `Type.GetProperty(name)` / `GetField(name)` in new code: it throws `AmbiguousMatchException` when a name is declared twice (`NormalInventoryItem.Item` next to `Element`'s `this[int]`, a `new` property). `MemberIndex.Find(type, name, flags?, kinds?)` returns the most-derived property (never an indexer) or field, cached per type (ConditionalWeakTable: plugin types stay unloadable); `Member.Get` reads by reflection for its first 64 reads (`CompileAfterReads`: a compile costs ~0.1-1 ms and saves under 1 us per read), then through a compiled expression-tree getter (reflection for good when compiling fails, `CompileError`), throwing like `PropertyInfo.GetValue`. `Readable(type)` (one member per name, sorted), `Of(type).AllProperties/AllFields` (reflection's own order), `Indexer(type, keyType)` / `Indexers(type)`, `Method` / `GenericMethod` (cached `GetComponent<T>`), `Call(method, target)` (a parameterless instance method: MethodInfo.Invoke for 64 calls, then a compiled delegate), `For(memberInfo)`. `MemberIndex.Types` is one type index (non-collectible assemblies, built once) by full and simple name keeping every candidate; `Resolve(name, filter, rank)` picks (`ResolveComponentType` prefers the HUD `Component` subclass: the old cache kept whichever "Player" loaded last). `bridge.self_perf` `requests` has per-kind request time and allocation (`query:eval`, `object.explore`...). `ReadableProperties(type)` is reflection's own order (settings, props layers), `TryGet(obj, name, ...)` a read that gives null instead of throwing, `StaticMethod` a cached static lookup. **Memory objects** (`Shared/MemoryObjects.cs`), one helper each, cached per type: `Address(obj)`, `StructSources(type)` / `CachedStruct(obj)` (the offsets struct an object caches: `*Cache*<T>` fields' Value or GameOffsets-typed properties, GameOffsets first, then the largest; memory.layout, memory.collect, layout.runtime and struct layers all use it), `StructType(name)` (structs by name through `MemberIndex.Types`, GameOffsets then ExileCore first), `SizeOf(type)` (computed once) and `NamingProperties` / `NamingMembers(type)` (RenderName, Name, Text, Path, Id: explore previews and list-layer item text). The settings walkers (settings.describe, hud.plugin_settings) share `SettingsMembers` / `NodeMember`; PluginBridge's `_methods` is read only through `BridgeRegistry()`.
