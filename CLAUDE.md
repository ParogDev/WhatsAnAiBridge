# What's an AI Bridge?

ExileApi (PoE1) **and** ExileCore2 (PoE2) plugin that exposes live Path of Exile game state over TCP for AI assistants.

## Quick Start

Run `/setup-mcp` to automatically set up the companion MCP server.

## Layout: one project, two games

```
WhatsAnAiBridge.csproj   single project; compiles Shared\ + the current game's folder
Directory.Build.props    decides $(Game) and TargetFramework (see below)
Shared\                  game-agnostic code: TCP server, DTOs, queries, recording, expression walker
Poe1\                    PoE1 partial class + GlobalUsings (ExileCore, SharpDX, net10)
Poe2\                    PoE2 partial class + GlobalUsings (ExileCore2, System.Drawing, net8)
```

- **Game detection:** the HUD folder is three levels up from the plugin (`<HUD>\Plugins\Source\<Name>`). If it contains `ExileCore2.dll` the build is PoE2; if it contains `ExileCore.dll` it is PoE1. Outside a HUD, pass `-p:Game=poe1|poe2` (default poe1); references then come from `$(exapiPackage)` / `$(exilecore2Package)`.
- **Both HUDs point their `Plugins\Source\Whats An AI Bridge` junction at the repo root.** Build intermediates are split per game (`obj\poe1`, `obj\poe2`).
- **`TargetFramework` lives only in Directory.Build.props.** The PoE2 HUD rewrites any `<TargetFramework>` in a plugin .csproj to `net8.0-windows` when compiling, which would break PoE1.
- **Shared files never import `ExileCore*` directly.** Namespaces come from the per-game `GlobalUsings.cs`.
- **Anything with a different API or different game knowledge goes in the per-game partial** (`Poe1/WhatsAnAiBridge.Poe1.cs`, `Poe2/WhatsAnAiBridge.Poe2.cs`), and the two must declare the same members.
- **No fake values for what a game lacks.** Omit the field (nullable DTO property), call `MarkUnsupported("feature")`, and list it in `UnsupportedFeatures`. Responses carry `game` and `unsupported`, and `hello` reports both.

## In-HUD stats panel (`Shared\StatsPanel.cs`)

- An ImGui window ("Player Stats", id `###bridge_stats_panel`) drawn from `Render()`. It is one surface over the **shared stats view** (`StatsUiState` in the settings: pins, filter, category, selection, sort, `PanelOpen`), the same state the MCP App and agents use.
- **Reads** the state every frame and the 250 ms stats snapshot (`GetStatsSnapshot`); the snapshot skips the HUD's `StatDictionary` (~60-150 us per read) while the raw (id, value) stat vectors are byte-identical to the last read (`SharedStatsRaw.cs`: vectors found once per Stats component by matching the dictionary, a full read and re-validation every 2 s, off with the broken link named in `bridge.self_perf` `statsRawCheck` on any mismatch); **writes only through the mutators** in `Shared\StatsFeature.cs` (`SetStatPinned`, `SetStatsFilter`, `SelectStat`, `SetStatsView`). Never add a second copy of the view state.
- Sync detection: the panel remembers the rev its own writes produced; any other rev change is "remote" (app/agent). A remote selection scrolls the row into view and pulses it; the header pill shows "Synced: <what>" for ~2.5 s.
- `PanelOpen` is the open flag, **closed by default**: the panel was a test surface and must not open on its own. Closing the window calls `SetStatsView(panelOpen: false)`; the settings UI has a "Show Player Stats Panel" pill and the control center a setting. Agents and tests never open it unless the user asks (`set_stats_view panelOpen=true` is a visible change on the user's screen). No hotkey.
- Panel-only preferences (section collapse, "Keys" label mode) are `StatsPanel*` ToggleNodes in the settings, not part of the shared view. Window position/size come from the HUD's `imgui.ini`.
- ASCII only in strings (the HUD font has no glyphs beyond it); icons are drawn with the draw list. Card fills derive from the live ImGui style (`SurfaceFill`); life/ES/mana and element hues are fixed. Filter/sort rows are rebuilt only when the snapshot or the view inputs change, and the table draws only the visible rows.

## Agent guide panel (`Shared\GuidePanel.cs`, state in `Shared\AgentGuide.cs`)

- An ImGui window (id `###bridge_guide_panel`) drawn from `Render()` after the stats panel: the agent's current instruction for the user as a sticky card. Agents drive it with `guide.set {title?, instruction?, step?, steps?, status?, detail?, clear?, stepId?, offerDone?, unseenAfterSec?, expiresSec?, ifStep?}` (status adds `unseen`: the user said done and nothing watched changed) and `guide.log {text, kind?: agent|step|result|warn}`; `guide.state` reads it back; `guide.user {stepId}` returns the user's answer to a step that offered Done (`{current, mark: null|done|cancelled, markAgoMs, unseen, status}`). **A step never outlives its asker:** `ifStep` makes a set (the asker's cleanup `clear`) apply only while the card still shows that step; `expiresSec` clears a waiting step whose agent went quiet (`GuideExpireTick`, from `SessionsTick`); a closed connection clears the waiting step its session set (`GuideOwnerGone`, from `SessionDisconnected`, outside the sessions lock); both post a warn toast. HUD-run steps (queue runner, flow, from Render) carry `who` and no session, so no disconnect clears them. `guide.state` reads it back. State is in memory only.
- **The log is not a panel.** Each new `guide.log` line is a toast under the card for 3 s, the last 0.6 s fading; newest on top, older ones slide down, at most 3 at once. The look is the brand's toast (`DrawGuideToasts`): a slate panel the strip's width with square corners and a hairline border, a 3 px stripe in the kind's tone flush on the left edge, an outlined 18 px glyph in the tone (circle-x error, triangle warn, circle-check result, circle-i agent and step), a caps title (faux bold, fake letter-spacing: one `AddText` per glyph from a cached ASCII table) and the message in caps under it, smaller and muted. `GuideCaps` upper-cases words but keeps identifiers as written (`fire_damage_resistance_%`, `GameController.Player`, `ReAgent`). The title is `guide.log`'s optional `title` (up to 40 chars), else the kind as a word (`STEP 2` while the guide is on a step, `RESULT`, `WARNING`, `ERROR`, `AGENT`); the tones are `ToneNeutral` agent, `ToneAccent` step, `ToneOk` result, `ToneWarn` warn, `ToneBad` error. Colours are fixed (`GuideToastInk` #15171c and friends) so toasts look the same on any HUD theme. Toasts go on the **background draw list** (no window: the mouse passes through) and show even while the card is hidden, anchored under the panel's last position. Toasts carry no hint text. A merged repeat (feed: "x3") shows its count as a chip at the right edge of the title line, tinted in the kind's tone (14% fill, half-strength hairline, the count in the tone at 0.85 f; the title clips short of it), and each repeat bumps the chip over 0.35 s (the tint flares, a ring leaves it) without re-entering the toast or pushing the stack (`Born` keys the slide-in and the push, `At` the life); the "N updates" summary toast after a combat hold swaps the circle-check for a two-stacked-sheets-with-a-check glyph in the same 18 px box. The quiet status dot (attention rule 5) is drawn in the same family at the card's glyph spot: a 6 px disc in the tone on a 1.5 px ink ring, an eased 6 px halo on hover, a 4 s shallow breathe only while the bridge is down, and a toast-styled ink label (foreground draw list, ASCII caps) instead of an ImGui tooltip when there is nothing to bring back. **Verbosity per kind** (`ToastShown`, settings `ToastAgent` off by default, `ToastStep` / `ToastResult` / `ToastWarn` / `ToastError` on): a kind that is off is skipped by the toast stack only (the stack height and the newest-toast push skip it too); the line still goes to the log sheet and `guide.state`. They are plain settings (not permissions): the Settings tab (Agent Guide section), the control center (`Meta` labels "Toasts: ...", group Agent guide) and agents through `settings.set` / MCP `hud_settings_set` can change them. The `agent` kind is what the MCP logs for every tool call ("Claude: run_csharp"): off, the user sees only steps, results, warnings and errors while playing. The **log sheet** opens only with the user's own hotkey, `Settings.AgentLogHotkey` (a `HotkeyNodeV2`, **none by default**: then the sheet cannot be opened and only the toasts show; set it in the Settings tab, "Agent Log Hotkey (toggle)", which uses the HUD's own `DrawPickerButton` picker with modifiers and Clear). The key **toggles** the sheet (press to open, press again, or the **Close** pill, to close): a dedicated key is not pressed by accident, so there is no hold delay, and a toggle lets the user select text and press ctrl+c without holding a third key. The sheet is its own window (`###bridge_guide_log`, `NoSavedSettings`, same anchor): the last 20 lines (at most 24 wrapped rows, oldest give way, so it never scrolls), newest at the bottom, in a read-only `InputTextMultiline` so lines can be selected and copied with ctrl+c, plus **Copy all** and **Close** pills. It fades over 0.2 s on close and takes no input while fading; it closes itself when the log is empty or the key is cleared. The key is read through `HotkeyNodeV2.PressedOnce()` (the HUD's `Input`, which polls the key while the game has focus; ImGui only sees keys sent to the overlay window, not the game's; it also honours the core's "ignore hotkeys on focused input"). `GuideLogOpen` is kept in the settings for old saves but unused.
- **The card is the persistent member of the toast family** (`DrawGuideCard`). The look follows syrairc's ExileImGui2 (ExileMaps: its toast stack and `MessageBar`, "the persistent cousin of a toast"), ported by hand, never referenced (no cross-plugin linking): slate ink panel with square corners and a hairline border, the status tone's stripe flush on the left edge, an outlined glyph in the tone, the status as a tracked faux-bold caps title, the body in the text colour and never the tone, and the loud state "tinted rather than filled". Rows: the **title row** (glyph or the flow's "now" badge, `DO THIS NOW` / `TRY AGAIN` / `CHANGE SEEN` / `CAPTURED` / `NOTE`; from the right: dismiss x or Stop, elapsed, the step pill, then the guide's title in dimmed caps in the space left, cached) and the **message row** (the instruction in sentence case - an instruction is read, not shouted). **Loud** (`waiting` / `failed` with an instruction): the message at 1.3 f, a 5 px stripe, a 22 px glyph, the title in the tone; the throb comes from attention (`Urgent`). **Calm**: f, 3 px stripe, 18 px glyph, white title. A third small line carries the status subline (progress dots, captured / failed detail), the agent's `detail`, or the flow plan. **The card grows before it clips** (the user: "sometimes instruction is unclear and it gets cut off"): the message wraps onto up to three lines, loud or calm (`GuideMsgLinesMax`; the captured receipt stays one clipped line), the third line onto two (`GuideSubLinesMax`) when its text is static (detail, the unseen line, captured / failed / unseen sublines; the animated progress and checking lines are short and stay one line). Wraps come from `GuideWrapCache` (`MsgWrap`, `SubWrap`), cached until the text, size, width or line limit changes, with `Clipped` saying whether ".." cut anything: no per-frame allocation. The animated sublines are three cached strings per line indexed by the dot count (`GuideDotted`). Width stays 480 px.
- **Hover, in the toast family** (`GuideHover(title?, body, note?, foot?, tone)`; `GuideTooltip(text)` is its one-line form). Never ImGui's grey tooltip over the card's own lines: an ink panel at most the card's width with a hairline, the tone's stripe on the left, an optional tracked faux-bold caps title and the body wrapped at 0.85 f (body in the text colour, note and foot muted), on the **foreground draw list** at full opacity, placed at the card's x **under the card's whole stack** (`HoverBelowY`: the window, then its toasts or the open log sheet) or above the card when there is no room below, clamped to the screen. Wrapped lines are cached until a text changes (`GuideSame`: same instance, else equal by value, so a per-frame string such as the restart card's tooltip is not re-wrapped). Users: the text block of the card (an InvisibleButton over message and third line, present whenever the card holds more than it shows: something clipped, a title with an instruction, a detail, or an asker worth naming) shows title / full instruction / detail / "Asked by <name>"; the title-row pills (`GuideCardPill`) and the x; `QueuePillButton` (queue, restart and log-sheet pills); the queue strip and the "Will record" line; the "who is asking" strip. The quiet dot keeps its own label (`DrawGuideDotTip`, placed at the dot). `captured` shouts for 4 s then shrinks to a one-line receipt (title dimmed) until the next step. **`done` is not a card:** when the status becomes done, `ObserveGuide` posts a 3 s `result` toast titled DONE with the instruction (the one-line result) and the card hides; `guide.state` still reports `done` for agents. **Reads** `GuideSnapshot()` and `GuideAskSnapshot()` once per frame; the writes are `GuideDismiss()` (the x), `GuideMarkDone()` / `GuideUnmarkDone()` (the Done side) and that done toast. A new instruction, or a return to waiting/failed, flashes the card.
- **The Done side of the card** (`GuideAskView` from `GuideAskSnapshot()`: a step set with `stepId` + `offerDone`, which `await_change` and the queue runner do). The title row's right end is laid out from the edge inwards: the way out first (the x, or the **Stop** pill while a queued step records), then the step's answer. `OfferDone` with no mark: a **Done** pill (`GuideCardPill` Primary: accent fill, a check, ink text - the one thing to press) left of the x / Stop, tooltip "You did it: the agent checks what it watches now instead of waiting"; on `detected` / `settling` it ends the settle wait and captures now. The x on such a card is **Cancel** (tooltip says so; `GuideDismiss` marks the step cancelled and the asker stops). **Mark `done` on a waiting card = "checking"** (`GuideChecking`, not a status an agent sets): the card goes calm (look `CHECKING`, accent, spinner glyph, message at f, no throb: `mustAct` in `DrawGuidePanel` is false while checking, so attention's `Urgent` is off), the third line says "Got it - I'm looking for that change..." in the agent's voice, and a **Not done yet** pill (Secondary: hairline, muted) takes the Done back. **`Unseen`** (waiting, no Done, `unseenAfterSec` passed): the card stays as loud as any waiting card (the user may still have to act) and the third line, in near-white (the agent talking, not an error), reads "I can't see that change yet - if you already did it, press Done"; it wins over `detail`. **Status `unseen`** (the step is over: the user said done, the agent saw nothing change): look `COULDN'T SEE IT` in the warn tone, calm (hairline frame, no pulse), an eye-with-a-slash glyph, the subline from `detail` (else "You said done, but nothing I watch changed. I'll look for another way to see it."), dismissible x. Not the user's fault, so never loud. Third-line priority: status subline, checking, unseen line, `detail`, flow plan. Pill tooltips go through `GuideTooltip` (alpha pushed to 1).
- **Attention** (`GuideAttentionFor`, one call per frame in `DrawGuidePanel`, the v1 of `research\display-attention.md`: rules 2, 3 and 7). **Every "how visible is surface X now" decision lives there**; surfaces read their entry of the `GuideAttention` record and never decide for themselves. Inputs travel with the outputs: `Highlights` (boxes on screen, from `HighlightSnapshot()`; the overlay re-resolves after this panel, so they can be a frame old), `Hovered` (io.MousePos against the card's rect last frame: a hit-test, the window takes no focus for it), `HoverAgo`, `NeedsUser` (waiting / failed / progress), `MustAct` (waiting or failed with an instruction: the user must act now; progress states are the agent working), `Overlapped`. Outputs: `CardAlpha`, `CardPulse`, `Urgent`, `CardInput`, `ShowPlan`, `ToastsAllowed`, `CardShift`. Rules now: **act now (rule 8)** - a `MustAct` card is never ghosted, highlight or not: 100% alpha, input on, plan line on, and `Urgent` makes the frame **throb** at 1.25 Hz with a fast attack (the tone's frame flashes to full strength and thickens, two halos swell 3 and 7 px outside it, the card gets a wash of the tone); confined to the card, never full-screen, never faster than ~1.5 Hz. It still never covers a highlight (`GuideAvoid` below). **Ghosting (rule 2)** - otherwise, while highlights are on screen the card targets 15% alpha, no pulse, no plan line, and `NoInputs` (clicks go to the game underneath); hovering it targets 90% and keeps that until 5 s after the mouse leaves; without highlights it is at 100%. The drawer eases the alpha over 0.3 s (`PushStyleVar(Alpha)` before `Begin`; `U()` goes through `GetColorU32`, which applies it; tooltips push 1 back). **Never cover a highlight** - `GuideAvoid` tests the card plus its toast stack at the card's *home* (where the user left it) against every box with an 8 px gap and picks the nearest free offset: right or left of each overlapping box (along the top edge, preferred), else below it, on screen. The window is moved by `SetNextWindowPos(Always)` only while that offset is non-zero (eased 0.3 s, `NoMove` meanwhile so home stays the user's), put back once when clear, and ImGui owns the position again. Toasts and the log sheet anchor under the card, so they move with it. **Combat (rule 1)** - input `Combat` from `CombatNear` (`Shared\GuideToastFeed.cs`: an alive hostile monster within 60 grid of the player, from the HUD's per-type `ValidEntitiesByType[Monster]` list sampled at 4 Hz, distance before `IsHostile`/`IsAlive`, held 3 s after the last one; town, hideout or no player release at once; an exception turns the sense off and names the break in `guide.state` `attention.combatBroken`); output `ToastHold`: `agent` and `result` toasts wait (those already up go down into the hold) and come back when it ends as one toast, "N UPDATES" with the latest line (a single held line comes back as itself). Cards, `step`, `warn` and `error` are never held. **Repeats and echoes (rule 6)** - the toast stack is a feed (`FeedGuideToasts`) built from the log as lines arrive: a line equal (kind, title, text) to the newest toast within 10 s bumps its count and restarts it ("RECORDED x3"; lines of kinds that are off don't break a run); while highlights are on screen (`DropEchoes`) a line equal to a visible box label or the highlight title is dropped. The per-kind verbosity applies before anything is held, counted or merged; the log sheet and `guide.state` keep every line. **Quiet dot (rule 5)** - inputs `Quiet` (the 2-minute quiet hide below, or no card at all), `Peekable` (a card or queued step exists), `BridgeDown` (`TcpBridgeServer.IsRunning` false); outputs `CardHidden` (never for a `MustAct` card) and `ShowDot` (only once an agent used the guide this HUD session, or while the bridge is down; not while toasts cover its spot): a 6 px dot where the card was, red while the bridge is down; hovering it (hit-test, no window) brings the card back and rule 7 keeps it 5 s after the mouse leaves; with nothing to bring back it shows a tooltip. `guide.state` carries `attention {combat, heldToasts, quiet, dot, bridgeDown, combatBroken}`. Growing it: add an input to the record and a rule to `GuideAttentionFor`; do not add visibility logic to a drawer.
- **Visibility:** `Settings.ShowAgentGuide` is the switch (Settings tab, "Show Agent Guide"). The panel hides itself when everything is quiet (idle/captured/done/info) and nothing the user could see changed for 2 minutes (a state change, or a toast that showed: lines of kinds that are off, held or dropped do not count, so an agent's tool calls don't keep a quiet card awake), leaving the quiet dot (Attention, rule 5); waiting, failed and progress states stay. It reappears on the next rev change or while the dot is hovered. The log state keeps the last 40 lines.
- **Guided flow on the card** (`Shared\GuideFlow.cs`; `FlowSnapshot()` and `FlowPlan()` read once per frame, nothing written): while a flow is `running` the strip's status glyph becomes the **"now" badge** (filled accent disc with the step number, the same badge as the in-game highlight) and the **live plan** (the best order of actions from where the user is now, re-planned every 100 ms by the engine) collapses to one small line under the instruction: "next: X  +N more", drawn only when attention allows (`ShowPlan`, i.e. not ghosted). The engine's "Not on screen yet" hint arrives in `detail` and takes that line instead when present (the status subline wins over both). When the flow ends `done`, "All N steps done" with a popping check holds the line for 3 s; then the card behaves as before (the engine's done/failed status rules). `ObserveFlow` still tracks plan changes and done-count drops for later use; nothing slides any more.
- **Stays out of the way:** a strip 480 px wide (a title row, the message row, at most one small line; the loud card is taller, never wider), default top-centre at y 10 (the very top of the screen); the user drags it anywhere and `imgui.ini` remembers. Flags `NoFocusOnAppearing | NoBringToFrontOnFocus | NoNav | NoScrollWithMouse`, no title bar, no background (the cards are drawn). It only takes the mouse over its own rectangle, and not at all while ghosted (see Attention). The instruction is one clipped line; a clipped line, or one with a title, shows the whole text in a tooltip on hover.
- **Queue card** (steps from `experiment.queue`, state in `Shared\ExperimentQueue.cs`): drawn under the live card when a step is `queued`, from `QueueSnapshot()` taken once per frame. Calm by design (neutral frame, no pulse, one accent control), and laid out as **two numbered steps so the order cannot be misread**: badge 1 is the **Start recording** button itself (`QueueStart(id, "hud")`, "first - nothing is recorded before this", **Skip** = `QueueCancel` at the row's right); badge 2 is the instruction, dimmed and prefixed "Then:", with "Only once this card says DO THIS NOW". The first live run failed because a big instruction read as "do this now" - the user acted before Start and the baseline already held the change. Never show a queued instruction prominently. Below: the optional note, "who asked N ago - do it 2x - then 4 more start by themselves" (chained steps, `QueuedStep.Chain`, counted in `QueueViewOf`), and "Will record: memory of PlayerStashTabs[33] (72 bytes)" (click opens the exact watch specs); "+N more" pill when several wait. A queued step keeps the panel visible past the 2-minute quiet hide. While the user has something to do (waiting/failed/progress, or a queued step is recording) the card shrinks to a one-line strip: "NEXT ..." when it will need Start, "THEN ... starts by itself" when it is chained to the running step. The running step shows on the live card, whose dismiss x becomes a **Stop** pill (`QueueCancel`) for its duration; the runner sets `offerDone`, so the **Done** pill sits left of Stop with the same checking / unseen feedback (Done captures now, or ends the repeat `unseen` naming the watch specs).
- Same rules as the stats panel: ASCII only (glyphs via the draw list), colours from the live ImGui style (`PanelTheme`, `SurfaceFill`) plus the fixed tones; no ExileCore* imports.
- **Highlights** (`Shared\GuideHighlight.cs` resolves, `Shared\GuideHighlightDraw.cs` draws): `guide.highlight {targets:[{item|path|rect:[x,y,w,h]|text (exact element label, e.g. a stash tab "DUMP", every visible match)|panel+child, label?, tier?: primary|secondary|context, order?, action?: click|rightclick, until?: checked|unchecked|gone}], title?, current?, auto?, durationSec?, clear?}`, `guide.highlight_advance`, `guide.highlight_state`. Targets re-resolve every 100 ms (`Element.GetClientRect()` coords draw 1:1 on the ImGui display, except under the world map's pan container `IngameUi.WorldMap[0]`: there the box is `parent + pan.X * W/2560 + local.X * H/1600`, `(pan.Y + local.Y) * H/1600`, with the pan read raw (no page cache) from WorldMap[0] + an offset calibrated against its Position at rest each time the map opens, and `HighlightSnapshot` moves those boxes with the pan every frame, because the HUD's rects trail a drag. Per-game hint `WorldMapPanOffset` (PoE2 0x100, PoE1 null = off until measured); `guide.highlight_state` reports `worldMapPan` (raw, or cached with the reason). `WorldMapPan` / `CalibratePan` / `OnWorldMap`; finding `ui.worldmap.pan-x-underscaled`). **Sequences auto-advance** (`auto` defaults on): a later step whose target appears becomes current, a met `until` or the current target disappearing ends its step, so `current` moves by itself as the user acts; the overlay keys its animations off `current`/`rev` changes, so quick successive advances read as successive pops. `DrawHighlightsImpl` runs from `Render()` after the guide panel on the **foreground draw list** (over the game UI, no window, no input), only while boxes exist. Interiors stay clear: primary = accent corner brackets, the only thing that pulses (2.6 s, low amplitude); secondary = thin accent frame; context = thin neutral frame. Ordered targets get an 18 px badge on the top-left corner: current = filled accent number, upcoming = neutral ring at under half strength, done = green check; a dotted hint runs from the current step to the next. **Action cue:** a box with `action` gets a 14x20 px mouse glyph outside it (right of the box first), its left or right button filled with the accent; on the current step the button dips and brightens once per 1.4 s with a small click ring (first press 0.7 s after entry, after the ring), upcoming steps show it static at 40%, done steps none. Entry: corners snap in over 0.3 s and the active primary gets one expanding ring (per target, so items snap in when their panel opens; an advance re-snaps only the finished and the new step; a highlight older than 2 s on first draw enters silently). One label pill per target, outside its first box, placed below/above/right/left where it covers no other box, badge, cue or pill (" x3" when an item matched several); the title sits above the active box with "step 2 of 3" or "done".
- **Verdicts (asked targets):** a target with `ask` (a yes/no question about the agent's guess, up to 80 chars) and an optional `key` (correlation id, e.g. `worldmap.stop.10=G2_4_1`) gets a **question strip** instead of its label pill: the step badge's accent disc with "?", the question, and Yes (check, `ToneOk`) / No (cross, `ToneBad`) / Not sure (dim) pills. **Only the pills are an ImGui window** (`##hl_ask_<index>`, no background, no decoration, `NoSavedSettings`, sized to the pills), so those clicks stop at the overlay and everything else stays click-through; the visuals stay on the foreground list. A click calls `HighlightAnswer(index, yes|no|skip)` (`GuideHighlight.cs`): the target's `Answer` is set (the rev does not change: the overlay would re-enter), a `HighlightVerdict` `{seq, id (= key, else hl<rev>.<index>), key, ask, label, answer, at, rect, item|path|text|panel+child, highlightTitle, highlightRev, target}` is kept in memory (last 300) and appended to `<BridgeDirectory>\verdicts\verdicts.jsonl` on a pool thread (the seq continues from the file after a restart), and while observing it is an `agent` event `{method: "user.verdict", params: <verdict>}`. The strip becomes a result pill for 2.2 s (popping glyph, fading out), then the label pill returns and a badge-sized check / cross / dash mark stays on the box's top-right corner (reserved in `Placed`). `guide.verdicts {since?, limit?}` returns `{seq, highlightRev, verdicts, asked (the current highlight's asked targets with answer and onScreen), pending}`; `guide.highlight_state` carries `ask`, `key`, `answer`, `answeredAt` per target and `verdictSeq`. **Highlights are per-session layers** (`_hlLayers`, one `HighlightState` per owner: the session id from `CurrentSession()`, `flow` for a running guided flow, `queue` for a queued step being recorded - those two carry the starting session's label as `Who` - and `anon` for a connection that never said hello). A `guide.highlight` replaces only the caller's layer and `clear: true` clears only it; `clear: true, force: true` clears every layer (the reply lists them and how many questions went with them). So an asked target survives any other session's call. Revs come from one counter across layers (`_hlRevSeq`), so verdict ids `hl<rev>.<index>` stay unique. `ResolveHighlights` re-resolves every layer's targets every 100 ms and drops a layer whose `durationSec` ran out; sequences, `current`, auto-advance and `guide.highlight_advance` are per layer. The overlay (`DrawHighlightsImpl(List<HighlightLayerView>)`) keeps one `HighlightUiState` per owner (entry animations, answered times) and draws all layers together: frames of every layer, then every badge and verdict mark reserved, then each layer's title and labels, placed against every layer's boxes (`_hlAll`, `_hlPlaced`); with two or more layers the title pill's subline names whose they are. Ask windows are `##hl_ask_<slot>_<index>` (`Slot`: a small number per layer, reused). Reads report the caller's layer at the top level as before plus `layers` (`{layer, session, who, mine, rev, title, current, targets, found, asked, pending, until}`, the combined view): `guide.highlight_state`, and `guide.verdicts`, whose `asked` / `pending` cover the caller's layers (its own plus a flow or queued step it started, matched by label) and `pendingAll` every layer; each verdict carries `layer`, `session`, `who`. Each layer with an unanswered question is a `pilot` blocker for HUD restarts (`Sessions.cs`).

## Fail at the broken link (maintenance rule)

Offsets move and HUD APIs change with patches. Code that looks things up must say **which link** broke, at the point it broke. A failure should never surface as "not found" ten calls later.
- Every lookup that can fail records the first failing link by name: the walker segment, the missing member, the panel that isn't open, a child index out of range (with the real child count), the collection item `where` that matched nothing, the value read vs the value wanted. See `Why` in `Shared/GuideHighlight.cs` and `Fail(...)` in `Shared/GuideFlow.cs`.
- Tell **broken** apart from **not now**:
  - A member, type or indexer that no longer exists (walker "No public property or field…", "Could not resolve component type…", "Cannot apply indexer…") is broken: report it at start (preflight) and loudly.
  - A null right now (a panel closed) is normal.
- Diagnostics are part of the result. `guide.flow_state` returns `diagnostics` (why the current step isn't done, why each option isn't available) and `preflight` (paths that no longer resolve).

## Bridge protocol (v2)

- Newline-delimited JSON-RPC 2.0 on `127.0.0.1:<port>`. The port and a per-launch random token are written to `<HUD>\<BridgeDirectory>\bridge-port.txt` / `bridge-token.txt` (default `claude-bridge`).
- **Every method requires the token**, including `ping` and `status`. Loopback is reachable by every local account, including the separate `gaming` user.
- `method: "query"` with `params.type` = `hello | player | area | playerstats | ui | stash | entities[:range] | monsters | items | deep:<filter>[:range] | eval:<expr> | describe:<expr> | record:* | recording:* | snapshot`.
- `experiment.queue|queued|result|start|cancel|collected` (`Shared/ExperimentQueue.cs`): guided steps an agent queues for the user to start from the guide card.
  - Nothing is captured before Start. The runner in `Render` then records the baseline, waits for a lasting change and lets it settle, once per repeat. It stores the raw eval / memory.read / memory.collect responses, which the MCP diffs.
  - Saved to `<BridgeDirectory>\experiments\queue.json`. A step that was running when the HUD closed goes back to queued.
- `data.find_value` / `data.find_result`: a background scan of all loaded tables for ids seen in memory.
- `observe.start|stop|status|events` (`Shared/Observer.cs`): passive observation while the user plays. The runner in `Render` runs while on and in game (panels 10 Hz, area and level 2 Hz, entities 0.5 Hz, layers at their own rates, the hud lane every frame):
  - **Layers** (`Shared/ObserveLayers.cs`) are runtime specs, not code: `{id, path, mode, hz, enabled?, key?, props?}`, any walker path in one of five generic modes, through reflection:
    - `struct`: the object's cached offsets struct read raw (leaf backend) and diffed, each changed range named by the runtime layout (HUD property, else struct field; null = unmapped). For server-sent state.
    - `props`: its public scalar properties. `dict`: an `IDictionary` (keys added, removed, values changed). `list`: a collection's items added and removed, by identity (`key`, default `Address`). `each`: a collection with a few values per item, `props` = 1-8 dotted sub-paths of the item, keyed by `key` (a dotted sub-path too); unit `<key>.<prop>`. A sub-path segment that doesn't exist is a broken link (preflighted on the first item).
    - Defaults: `server` (`ServerData`, struct, 10 Hz: 34 KB on PoE2), `stats` (the player's `StatDictionary`, dict, 4 Hz), `life` (`Life`, props, 4 Hz), `buffs` (`BuffsList`, list by `Name`, 4 Hz) and `inventories` (`ServerData.PlayerInventories`, each, 2 Hz: `Inventory.Hash` and `Inventory.ItemCount` per `TypeId`, unique on PoE2's 118). Defaults apply only to a fresh state; existing specs are kept. `observe.layers`, `observe.layer_set` (preflight: a path or mode that doesn't fit is refused, naming the link), `observe.layer_remove`. Specs persist in `observestate.json`.
    - The mode check runs once per resolved type: for `struct` it boxes the whole cached struct (34 KB for ServerData), which every tick made the observer allocate ~1.6 MB/s.
    - Events: `layer` `{layer, mode, unit, name, old, new, ...}` (struct adds `off`, `len`, `i64` of the aligned 8 bytes whenever the change fits them and `i32` of the aligned 4 when it fits those, so every change of a unit has one comparable width; dict/props add `delta`, `change`). A unit (struct: its 256-byte block) changing over 20 times in 10 s becomes one `layer.noisy` and is then only counted. `observe.layer_map {layer, unmappedOnly?, minChanges?, sort?, limit?}` lists every unit that changed (`observe.server_map` = layer server): the mapping worklist.
    - Values are compared as objects and formatted only when they change; a 4 ms per tick budget spreads layers over frames. A layer whose path breaks stops with `broken` (status) instead of retrying.
  - **Every event** carries `t` (ms on one process-wide clock) and `frame` (ImGui frame count), so layers line up; the journal is written once per tick, not per event.
  - Top-level UI panels opening or closing, with the IngameUIElements property that maps each one, or none, at 10 Hz once the visibility bit is calibrated (2 Hz on the `IsVisibleLocal` fallback); the panel list itself is refreshed once a second. An unmapped panel is saved with its first texts and 512 bytes at its address.
  - **hud** lane (`Shared/ObserveHud.cs`): a frame at least 50 ms and 2.5x the moving average becomes `{cause: spike, intervalMs, typicalMs, gcMs, gen0..2}` (one per 2 s, the rest counted in `suppressed`; gaps over 1.5 s are the overlay hidden or a load, skipped); plugin reloads `{cause: reload, plugin, ok, durationMs}`. So HUD hiccups aren't read as game events.
  - **agent** lane: every bridge call that changes what the user sees or what the HUD does (`AgentMethods`: guide, highlight, flow, experiment, reload, settings, focus, script, measurements, stats view, layer specs) as `{method, params}`, long strings clipped, secret settings values redacted.
  - Area and level changes, and new entity metadata prefixes (every 2 s).
  - Events go to a ring of 1000 and to `<BridgeDirectory>\observe\journal.jsonl`, rotated to `journal.1.jsonl` at 128 MB (one generation kept; at start the sequence continues from both). The on/off state survives restarts (`observe\state.json`).
- Structured methods with named params: `stats.*` (shared stats view), `recording.*` (stateless playback), and `hud.*` (dev loop):
  - `hud.plugins` lists loaded and failed source plugins.
  - `hud.reload_plugin {name}` queues a recompile of one source plugin, like the menu's Reload button. It runs in `Render` on the main thread, and the HUD pauses while compiling. The bridge refuses to reload itself. The setting is `AllowPluginReload`.
  - `hud.reload_status` reports the queued reload and the last result. The watchdog answers it even while the HUD is compiling.
  - `PluginManager.ReloadSourcePlugin` is internal on both HUDs and is called by reflection. Check it with the MCP's `hud_type` after HUD updates.
  - **Reloading changed code needs the HUD setting Core → Plugin Settings → "Avoid locking plugin dlls" turned on.** It is off by default on both HUDs, and takes effect for plugins loaded after it is turned on, so restart the HUD once after ticking it.
    - When it's off, the HUD loads each plugin DLL from its file and keeps it locked. A recompile then can't replace the DLL, and the HUD has already unloaded the plugin, so it stays off until a restart.
    - So `hud.reload_plugin` refuses with `dll_locked` while the setting is off; `force=true` overrides that when the code didn't change. `hud.plugins` reports the setting as `avoidLockingDllFiles`.
- `script.run {code, thread: main|worker, timeoutMs}` and `script.result {id}` run C# inside the HUD using the Roslyn scripting DLLs both HUDs ship (`Shared/ScriptRunner.cs`).
  - **Off by default** (setting *Allow C# Scripts*): it's arbitrary code in the HUD process.
  - **Compile and run:** compiling happens on a worker; the run happens at the start of `Render` (main thread) or on the worker. A running script can't be aborted.
  - **What scripts get:** a prelude (`GameController`, `Log(object)`) and the game namespaces present in this build. The last expression is the result, serialized like `eval:` results.
  - **No globals type:** Roslyn needs a file-backed assembly for one, and plugin assemblies load from memory when the HUD avoids locking DLLs.
  - **Caching:** identical code reuses its compiled script.
  - **CI:** the runner's reference set includes the Roslyn DLLs (scaffolding `tools/ci/sync-hud-refs.ps1`).
- `pipeline.trace {durationMs?, entities?, series?}` / `pipeline.trace_result {id}` (`Shared/PipelineTrace.cs`): times the HUD render pipeline for the render-fidelity research (MCP `pipeline_trace`).
  - **Off by default** (setting *Allow HUD Instrumentation*). For the trace only, Harmony (Lib.Harmony, copied next to the compiled plugin by the .csproj and loaded into the default load context: it cannot load into the collectible plugin context) patches the HUD's own unprotected code: `ImGuiRenderer.Update` / `Render`, `Overlay.ReplaceFontIfRequired` (the first call after Present: Vortice's Present is a calli and the PoE2 HUD's `PostFrame` is protected), every plugin's `Render`. Then `UnpatchAll`.
  - **Memory reads are wrapped, not patched** (PoE2's backends are obfuscated; Harmony's IL copy fails): `Memory.CustomBackend` gets a timing wrapper over the paged backend, and the paged backend's leaf field another; both are restored at the end. Refused when the HUD is showing a snapshot.
  - **Never patch a protected method**: `TraceIsStub` refuses the IL stubs (patching one hangs the HUD). Every target that could not be instrumented is listed in `patches.refused`, and `calls` counts each hook so a hook that is never hit names the broken link.
  - `series=true` adds per-frame arrays (`tMs`, `intervalMs`, `workMs`, `pluginsMs`, `gcPauseMs` from `GC.GetTotalPauseDuration` recorded at each frame start) for timelines.
  - The `gc` block reports `fetchedPagesPerFrame` and `sharedArrayPool` (how many arrays per size `ArrayPool<byte>.Shared` keeps, read from the runtime's `SharedArrayPoolStatics`, with `broken` when that internal type moves). Fewer kept than cycled means page churn (scaffolding `research/hud-gc.md`).
- `tracker.start {durationMs?, entities?, draw?}` / `tracker.result {id}` / `tracker.stop` (`Shared/FreshTracker.cs`, MCP `overlay_accuracy`): each frame, at the end of `Render`, projects the nearest players from the HUD's cached camera and position and from both read fresh (`DisableCaching`), and records the pixel error and its camera and position shares. Offsets are calibrated at start by matching the HUD's values in fresh bytes, and it fails naming the link if a match is lost. Positions come from the per-game `RenderPosNum`. Read-only; `draw` marks both on the foreground draw list.
- `layout.runtime {type?|path?}` (`Shared/RuntimeLayout.cs`, MCP `hud_runtime_layout`): the CLR's real layout of an offsets struct, each field set alone to 0xAB bytes in a boxed instance (nested game structs flattened as a.b), next to the metadata offset. With a walker path it takes the object's cached struct (`CachedValue<T>`/`FrameCache<T>` field or offsets-typed property), maps each public property to the field holding the same non-zero value (fields overlapping at one offset count as one), and checks the field against fresh memory at Address + offset. PoE2's disk metadata has decoy offsets; the runtime layout is the truth.
- `motion.watch {range?, minSpeed?, on?}` / `motion.state {since?}` (`Shared/MotionWatch.cs`, MCP `await_motion`): a per-frame check, while armed, for another player starting to walk nearby (3 frames above minSpeed; the local player is ignored). It lets measurements start on a moving target without anyone moving the character. `tracker.start entityId=` then follows that player.
- `lab.set {walls?, path?, bars?, target?, delayMs?}` / `lab.state` (`Shared/RenderLab.cs` data, `Shared/RenderLabDraw.cs` visuals by Fable, contract in `Shared/RenderLabTypes.cs`; MCP `render_lab`): experimental world renderers, off by default, for A/B tests against Radar and HealthBars.
  - Fresh camera and player position at draw time, time-aligned by `delayMs`.
  - Nothing is drawn (or computed) while a fullscreen or large panel is open (`LabBigPanelOpen`: `IngameUi.FullscreenPanels` / `LargePanels`, sampled every 50 ms): the lab never covers the passive tree, the atlas or a vendor.
  - Walls: rays over `RawPathfindingData`, re-cast per grid cell.
  - Path: A* on a worker, line-of-sight simplification and Chaikin smoothing, trimmed to start at the player's live position.
  - Bars (`Shared/RenderLabBars.cs`, foreground draw list so it shows over the bar it marks): a thin gold bracket at HealthBars' own anchor (Entity.Pos = Render.Pos + Bounds.Z, raised by 2 x Bounds.Z unless "Place Bar Relative To Ground Level", plus its Z offset; HealthBars' settings read by reflection once a second) for up to 30 nearby hostile monsters and players, so the user can see whether HealthBars' bar stays centred on the entity while moving.
  - Allocation-free per frame: fresh reads go through `RawRead` (no page cache, no arrays), wall and path buffers are reused, bars use a plain loop with cheap tests first (no LINQ, no `DistancePlayer`). Check with `bridge.self_perf` after changing it.
  - The drawer gets screen-space data only.
- `lab.compare_paths {target?, stepWorld?, replanMs?, speed?}` (`Shared/RenderLabCompare.cs`, MCP `render_lab compare=true`): offline A/B of path drawing on the area's real grid. It simulates walking the route and measures, for Radar-style (per-cell A* from the integer cell, re-planned at most every 100 ms, drawn from the live position) and the lab, the backwards first segments, the turning per 100 units, and how far the drawn line moves between steps.
- `profile.plugin {name (display or plugin type name), method?, durationMs?}` / `profile.result {id}` (`Shared/PluginProfiler.cs`, MCP `profile_plugin`): Harmony wraps every method and instance constructor of one plugin's assembly for a few seconds, with a per-thread call stack, and reports per method calls and self/inclusive time. The hooks' own cost (~0.23 us and ~97 B per call, measured on an empty method at start, `hookOverhead`) is subtracted from every call: before this, tiny hot getters looked ~96 B per call heavier than they are. Then `UnpatchAll`. Behind *Allow HUD Instrumentation*; skips IL stubs, generic definitions and tiny bodies. `method=<name substring>` narrows any profile; `assembly=<name> filter=<type substring>` profiles part of a HUD assembly instead. The bridge profiles itself only with `method=` or `filter=`, and never patches its profiler or trace code (`IsInstrumentationCode`). On PoE2 the ExileCore2 core is control-flow obfuscated: Harmony refuses every method (`InvalidProgramException`, nothing applied), so only PoE1's core, unobfuscated libraries and plugins can be profiled.
- `gc.pool {maxArraysPerPartition?, maxBucketBytes?}` (`Shared/GcPool.cs`): reports, and behind *Allow HUD Instrumentation* changes at runtime, how many arrays per partition `ArrayPool<byte>.Shared` keeps for buckets up to `maxBucketBytes` (default 16 KB): under each partition's own lock its `_arrays` is replaced by a longer or shorter copy. Lasts until the HUD restarts; 32 is the runtime default. An experiment tool for the page-cache GC churn (scaffolding `research/hud-gc.md`), not a fix: a bigger pool cuts allocation and GC count but each pause promotes more and gets longer.
- **Measuring needs the game in front** (`Shared/MeasureFocus.cs`): `pipeline.trace` and `profile.plugin` announce themselves on the guide card (only when it is idle; otherwise a toast), clear the card when they finish and report in a toast (never a card that stays) and sample every 100 ms whether the game is the foreground window; results carry `foreground {share, atStart, atEnd}`. `focus.game {}` brings the game window to the front (window manager only, no input; call it only when the user asked or agreed). `game.config {}` returns the game's display settings that affect measurements (background framerate cap, vsync...), read from the config in the game process owner's profile, allowlisted keys only.
- `settings.describe {plugin?}` / `settings.set {plugin, path, value, allowPermission?}` (`Shared/SettingsControl.cs`): every loaded plugin's settings by reflection (nodes recognised by shape; labels from the HUD's `[Menu]` attribute, and for this bridge from its `Meta` table; nested settings objects become groups). Changes run at the next Render, or on the bridge thread when the HUD isn't rendering (overlay hidden: the game isn't in front), marked `appliedOn`. Permission settings (`AllowCSharpScripts`, `AllowHudInstrumentation`, `AllowPluginReload`) refuse to change without `allowPermission`, which the MCP server only sends from the control center's own route after the user confirms, never from a tool. Text under secret-looking names, or holding a secret in its value (`Password=`, `token=`...), is returned as `[redacted]` (write-only); `hud.plugin_settings` uses the same check.
- **Sessions, leases and restarts** (`Shared/Sessions.cs`; card and strip in `Shared/GuidePanelSessions.cs`): who is talking to this HUD and who may restart it. **Names the player reads** (`RenameLocked`, `BaseDisplayName`): a session's `Name` is its label without a worktree's random `-1a2b3c` tail, never a system folder (cwd under Windows or Program Files: "Claude Desktop"; drive root, user folder: "Claude"), `ps:x` as "x (script)", and unique among the connected ("main", "main (shell)", "main 2"); `session.list` and `session.hello` return it as `name`, labels stay the identity. `AgentsSnapshot()` (`AgentsView`, rebuilt by `SessionsTick` at 4 Hz, read per frame by reference) lists only connected sessions with something going on (asks = pilot blockers, doing = the rest), plus HUD-run work still asking under a name nobody is connected as; idle and disconnected sessions never reach the in-game UI. `TcpBridgeServer` numbers every connection (`PendingRequest.ClientId`, `ClientClosed`), `DrainRequests` sets `_reqClientId` for the request being served, and `CurrentSession()` / `CurrentWho()` resolve it to the session that said `session.hello {id, label, branch?, cwd?, pid?, kind?}` on that connection (the MCP server does on every connect, identified by its working directory's git branch; `restart-hud.ps1` as `ps:<who>`). Everything that asks the user for something records who: `GuideState.Who`, `QueuedStep.By` (default), `FlowState.Who`, `Measure.Who`, `ReloadRequest.Who`, `_recordingWho`. These are session **labels** (a branch, a folder); the in-game UI never shows a label. **`AgentsSnapshot()`** (`AgentsView`, rebuilt by `SessionsTick` at 4 Hz, read per frame by reference) lists the active agents, each with a readable `Name` (`NameOf(label)`: never a system folder, no worktree hash tail, unique among the connected), what it `Asks` of the user (pilot blockers) and what else it is `Doing`; idle and disconnected sessions are not in it. The card's title row names the asker (`NameOf(g.who)`, cached) only while `Ambiguous` (two or more agents active); one obvious agent gets no name. **Blockers** are computed on demand from that state (`BlockersLocked`: a measurement, a pending reload, a recording, a running queued step, a running flow, a guide status the user is acting on) plus explicit **leases** (`lease.acquire {kind: perf|pilot|record|reload|other, label, ttlSec?}`, `lease.renew`, `lease.release`; they expire, so nothing leaks). **Restart requests** (`restart.request {reason?}` → `{id, status: waiting|go|merged|denied, blockers, holdUntil, secondsToGo}`, `restart.status {id}`, `restart.cancel {id}`): `SessionsTick` (Render, 4 Hz) re-evaluates waiting requests; blocked ones list their blockers, free ones hold `Settings.RestartHoldSec` (default 5 s) then become `go`; one `go` at a time, the rest `merged` into it; a `go` the requester never acted on expires after 3 min. `lease.acquire` is refused with `restart_pending` while a `go` exists. The card (`DrawRestartCard`, under the live card, keeps the panel visible): blocked in the warn tone with the blockers as bullets ("Claude: measuring HUD frame timing (12 s left)", names through `NameOf`), counting down in the accent tone; **Restart now** = `RestartAllow` (granted over the blockers; the log tells their holders), **Not now** = `RestartDeny`. The **"who is asking" strip** (`DrawSessionsStrip`, "WHO IS ASKING  Claude, Tester") shows only while the panel is up anyway **and two or more agents ask the user for something** (`Asks.Length > 0`): its one job is to keep two requests from reading as one voice. Hover: "Name: what it asks" per ask (`AskWords` drops the "waiting for the user:" prefix, turns a question into "asks: ..."), "- also <doing>" after the first. Never idle or disconnected sessions, branches or folders (the user: "I have no idea what 'system32 layer-test - main - main' mean"). Line and hover text are recomposed only when the `AgentsView` instance changes. `session.list` is the full view for agents (MCP `hud_sessions`). State is in memory: a restart ends it.
  - **MCP builds and the rollout.** `session.hello` takes an optional `mcp {version, sha, mode: supervised|local|unsupervised, deployedVersion, deployedSha, workerPid}` (old servers send none): which MCP server build the session runs and what `%LOCALAPPDATA%\ExileApiMcp\current.json` said was deployed when it connected (`supervised` follows deployments; `local` is pinned to its own checkout's build; `unsupervised` is an old launcher that needs a session restart to get a supervisor). Kept per `SessionInfo`; `session.list` returns it as `mcp` per session and a top-level `mcpRollout {deployedVersion, deployedSha, total, onDeployed, behind, local, unsupervised}` (the deployed build from the newest hello that carried one, against the connected sessions that reported `mcp`; `behind` = supervised and not on it yet, i.e. a rollout in progress; null until a hello carried a deployed build). `hello`'s reply carries `mcpRollout` too. A **hot swap** connects a new worker that says hello with the same session `id`: the session moves to the new connection and the old one stays its own (`PrevClientId`) until it closes, so the old worker's in-flight calls keep their "who" and its close disconnects nothing.
  - **The panel never takes the sessions lock per frame.** `SessionsPublishLocked` publishes an immutable `SessionsView` (session copies, the oldest waiting restart, the granted one, the rollout) at 4 Hz from `SessionsTick` and on every change (hello, a connection closing, a request, Restart now / Not now, cancel); `SessionsSnapshot()` returns it.
  - **The sessions chip** (`DrawSessionsChip`): the always-there quiet member of the toast family. A small ink pill beside the card's strip at title-row height (right of it, left when that leaves the screen; background draw list, no window, hover by hit-test like the quiet dot), card or no card: the two-rings glyph and the agent count at half strength. It says more only when something could disrupt play: an agent waiting to restart adds the restart glyph (warn tone, still, while blocked by someone's work; accent, turning, with the seconds while counting down); a granted restart turns it with RESTARTING and a slow shallow breathe (never a throb); an MCP rollout in progress (supervised servers not swapped yet, which cuts nothing) is a 2 px accent hairline along its bottom edge filled by onDeployed / (onDeployed + behind). It ghosts with the card (`CardAlpha`). Hover: the panel's hover sheet (`GuideHover`, under the card's stack like every other hover) with who does what (readable names through `AgentsView.NameOf`, what from `BlockersSnapshot`), each MCP's build and mode - unsupervised sessions, the ones needing a session restart, are named only here - the restart line and the rollout line, its texts rebuilt once a second while hovered. Count and countdown strings are rebuilt only when their number changes: nothing allocates per frame.
- `bridge.self_perf` (`Shared/SelfPerf.cs`): the bridge's own time and allocation per Render step, averaged since the previous call (always on, allocation-free). Check our own cost with this after changing per-frame code, then `profile.plugin name="Whats An AI Bridge" method=<step>` for the method.
- `RawRead<T>` (`Shared/RawMemory.cs`): allocation-free small reads straight from the leaf memory backend. Use it for scattered per-tick reads: `Memory.Read` on an uncached page rents a 4 KB page that mostly ends up as garbage.
- `object.explore {path, offset, limit, csharp?}` (`Shared/ObjectExplorer.cs`) returns one level of the object model at a walker path, for mapping data out:
  - **For the node and each child:** type, kind, a one-line preview (structs as `X=1 Y=2`, objects with their Name/RenderName and visibility), counts, the walker `path`, and null-safe `csharp`. Dictionaries with enum keys get typed keys (`Stats?[GameStat.MaximumLife]`).
  - **Entities** also list their components, as `GetComponent<T>()` paths.
  - **Paging:** collections are paged with `offset`/`limit`.
  - **Time budget:** reads run on the main thread under a 60 ms budget, and unread members are listed in `skipped`. Getters taking 5 ms or more get `slowMs`.
  - **Shared resolver:** `ExpressionWalker.Resolve` is the one path resolver behind `eval:`, `describe:` and explore.
